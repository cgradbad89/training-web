## Section 1 — App Overview

**Purpose**: Personal running and fitness dashboard for a single authenticated user. Syncs workouts from Apple Watch via iOS HealthKit, visualizes training load, manages race goals and training plans, and provides an AI coaching interface.

**Auth**: Google OAuth via Firebase Auth. A single owner email (`folstromjohn@gmail.com`) gates the HubBanner nav links.

**Hosting**: Vercel (production: https://training-web-rho.vercel.app)

**Shared app data (`AppDataContext`).** The six data-heavy `(app)` pages — This Week (dashboard), Personal Insights, Plan Insights, Runs, Shoes, Workouts — previously each fetched the same domain collections independently on mount with no shared cache (six `healthWorkouts` reads, four `plans` reads, etc. per session). All non-Health routes retain the original shared-provider mount and behavior. Pages retain any non-shared local fetches (e.g. dashboard `healthMetrics`/ring-goals, shoes shoe-inventory + manual assignments). Personal Insights also derives its main cache fingerprint entirely from these already-loaded context values; VO₂ remains a separate bounded `healthMetrics` read because metrics are intentionally not global context data.

**Workouts fetch pattern (as of 2026-07-17): one-time fetch + focus refresh, not a live listener.** `workouts` is populated via a single `fetchHealthWorkouts(uid, { limitCount: 1000 })` call (`getDocs`, not `onSnapshot`) when the provider mounts. Freshness comes from two mechanisms instead of continuous push: (1) `useRefetchOnFocus` (`src/hooks/useRefetchOnFocus.ts`) — a generic `visibilitychange`-driven refetch hook with a 30s floor between refetches, wired to `refreshWorkouts` at the provider level so every consumer benefits without reimplementing it; (2) a manual refresh button (`RefreshCw` icon, spins while in flight) on This Week, Runs, and Workouts, wired to `refreshWorkouts()`. `workoutsLoading` is initial-load-only, while `workoutsRefreshing` reports later focus/manual refreshes; existing workouts remain rendered during the latter. `refreshWorkouts` owns an in-flight promise guard, so overlapping triggers reuse one read. This was a deliberate trade-off: dashboard and runs previously ran a **live** `onHealthWorkoutsSnapshot` listener specifically so real-time iOS-sync updates showed while the page was open; that live-push behavior is now gone in exchange for fewer Firestore reads. The accepted condition is that navigating to or refreshing any consuming page always shows current data (satisfied by fetch-on-mount) — a workout that syncs while the tab sits idle in the background won't appear until the next focus-refresh or manual refresh. The shared read limit was raised **500 → 1000** in the same change: Workouts page used to run its own `where("isRunLike","==",false)` + `limit(500)` query, giving it up to 500 non-run workouts specifically; now it filters the shared (run+non-run) array client-side, so the cap had to double to avoid a heavy-run user's non-run history falling out of the shared top-N window. No delta/toast UI depended on live snapshot changes (verified before the conversion), so nothing needed replicating for the one-time-fetch model.

**Health metrics covered-range cache (as of 2026-08-20).** The Health page owns a component-lifetime `HealthMetricsCache` (`src/utils/healthMetricsCache.ts`) rather than separate rolling/YTD/All/Calendar stores that cannot reuse coverage. Entries are keyed by local `YYYY-MM-DD`; `coveredRanges` are sorted, inclusive, and non-overlapping. A successful query marks its entire requested range covered even when some dates have no documents, because re-reading those empty dates within the same page mount adds no value. The rolling `fetchHealthMetrics(uid, 90)` query, YTD gaps, and All results seed the cache; Calendar calls `getUncoveredGaps` and reads only missing ranges before merging via `mergeCoveredRange`. The rolling fetch separates `metricsInitialLoading` from `metricsRefreshing`: only the first successful load can show `HealthSkeleton`, while later focus/manual refreshes keep cached content mounted and a background failure does not replace it with the full-page error state. An in-flight promise guard deduplicates overlapping Health refresh triggers. Each existing fetch site retains its own lifecycle—there is deliberately no central visibility-refresh coordinator. The rolling cutoff uses local-calendar arithmetic (`healthMetricsCutoffISO`) to match the stored date invariant rather than a UTC `toISOString()` boundary.

**Auto-match live-listener exception.** `AutoMatchRunner` retains a narrow live listener so a non-run workout that arrives after the page opens can complete a due cross-training session without a manual refresh. The query is server-filtered with `isRunLike == false` and capped at 500; run-only changes never enter its result set. The listener activates only when the shared plans array has settled and `planNeedsAutoMatch` finds an **active workout plan** with at least one `type:"workout"`, incomplete (`completed !== true`) entry whose derived local planned date is today or earlier. With no such plan/entry, there is no listener at all. This deliberately reuses the matcher's existing due-date rule: an active plan whose first session is still in the future does not listen until that session becomes due (product-owner confirmation of that future-start policy remains pending). The existing snapshot content-key and in-flight guards still prevent duplicate/bursty matcher passes; overrides and `refreshPlans` remain latest-value refs, so their identity changes do not resubscribe. `/health` remains excluded at the layout boundary as documented above.

**Page-content reflow (responsive).** Beyond the shell, the main data pages reflow below `lg` (the same desktop/mobile divider): (1) the **This Week 7-day grid** (`src/components/WeekCalendar.tsx`) is a horizontal **scroll strip** — `overflow-x-auto` wrapper around a `min-w-[560px] grid grid-cols-7`, so the week swipes sideways on a phone and shows all 7 columns inline at `lg`; (2) the **dashboard KPI rows** (Running / Workout metrics) use responsive column counts (`grid-cols-2 sm:grid-cols-3 lg:grid-cols-6` / `lg:grid-cols-5`) so tiles wrap instead of crushing, returning to 6/5-across at `lg` (the former Health avg/day KPI tiles were replaced by the single `HealthHeroTile`); (3) the **Plans two-pane** stacks below `lg` via a `mobileView: "list" | "detail"` state on the Plans page — the plan-list rail is full-width by default (`w-full lg:w-64`), selecting a plan swaps to a full-width detail (`hidden lg:flex` toggling on each pane) with an `lg:hidden` "back to plans" button; at `lg` both panes are always shown (two-pane unchanged). Desktop (`>= lg`) renders identically to the pre-mobile layout in all three cases — the reflow is purely additive at `< lg`.

## Section 3 — Data Model

All user collections live under `users/{uid}/…`. Exception: `stravaActivities` is a legacy global collection.

### `stravaActivities/{activityId}`
Legacy Strava data synced from iOS. **Not uid-scoped** (single-user legacy design).
Key fields: `id`, `name`, `type` (ActivityType), `start_date`, `distance_m`, `moving_time_s`, `avg_speed_mps`, `avg_heartrate`, `pace_sec_per_mile`, `gear_id`, `efficiencyScore`.

### `users/{uid}/healthWorkouts/{workoutId}`
Primary workout data written by iOS HealthKitSyncService.

## Section 4 — Domain Invariants

1. **User scoping**: All data lives under `users/{uid}/…`. The only exception is `stravaActivities`, a legacy single-user global collection.
2. **Week boundaries**: Monday-start throughout. `weekStart()` in `src/utils/dates.ts` uses `(day + 6) % 7`. Matches iOS `WorkoutViewHelpers` convention. **Plan start dates are Monday-normalized**: `RunningPlan.startDate` by long-standing contract for **all** creation paths (as of the 2026-08-20 session, matching WorkoutPlan below), and `WorkoutPlan.startDate` for **newly created** plans (as of a same-day 2026-08-20 session) too (`snapToMonday` in `src/utils/planDateEdit.ts`, the same helper the copy/slide paths already use). Existing plan documents of either type were NOT migrated; see §6 #41. **"Which plan week is this" is derived by exactly one helper**, `planWeekIndexFor(startDate, referenceDate)` in `src/utils/planMatching.ts` — never re-implemented inline, and never with `new Date(plan.startDate)` (see invariant #12). That helper diffs whole calendar days (DST-immune) before flooring by 7, not a raw millisecond difference — see §6 #41(b).
3. **Workout overrides are non-destructive**: `workoutOverrides` docs layer on top of `healthWorkouts` at display time via `applyOverride()`. The source document is never written by the web app.
4. **planType backward compat**: Existing RunningPlan docs lack `planType`. `src/services/plans.ts` defaults to `"running"` on every read path. Never rely on `planType` being present.
5. **setActivePlan type isolation**: Activating a running plan deactivates only other running plans. Workout plans are independent. Uses atomic batch write.
6. **Plan auto-match (running)**: 2-pass best-fit matcher in `src/utils/planMatching.ts` (`matchPlanToActual`) — day proximity (same-day, then ±1-day) is the **only** gate on whether a run matches its planned entry; match quality (`"full"` vs `"partial"`) is then decided solely by `meetsCompletionThreshold`: actual mileage ≥ **85%** of planned (`COMPLETION_THRESHOLD_RATIO`). A run below 85% still matches (shows `"partial"`, not `"missed"`) as long as it falls within the day window. A global `used` set prevents double-counting the same workout against multiple plan entries. The distance the 85% threshold is applied to is the **override-corrected** one: `matchPlanToActual` takes an optional `overrides` map (keyed by `workoutId`) and layers it on via the shared `applyOverride()` before grading, so a `distanceMilesOverride` moves the graded distance but never the threshold itself (see §6 #40). **Both sides of the day comparison are LOCAL calendar days**: a planned entry's date is built from local components (`plannedEntryDate`) and a workout's date key is `toISODate(w.startDate)` — the same `getFullYear/getMonth/getDate` mechanism `services/autoMatch.ts` (`localISODate`) and every mileage/stat surface use. It must never be the UTC day (see §6 #42). (Replaces the former distance-tolerance/shortfall rules — see §6 Known Sharp Edges.)
7. **Shoe assignment priority**: Manual assignments (in `shoeAssignments/manual`) always win over auto-assign rules. `evaluateAutoAssignRules()` skips any workout already in `existingAssignments` (including explicit `null`), so an explicit "no shoe" survives a matching auto-rule. Auto-assignments are derived (never persisted); both the listing and detail pages must resolve via `{ ...autoAssigned, ...manualMap }` — the detail page uses `useResolvedShoeAssignment` to stay in sync (a prior bug had it read only the manual map, so auto-assigned shoes never showed on the detail page).
8. **stripUndefined requirement**: All Firestore writes pass through `stripUndefined()` = `JSON.parse(JSON.stringify(obj))`. Firestore rejects `undefined` values.
9. **Auth guard**: All `(app)/*` routes require a valid Firebase Auth session. The `AuthGuard` component enforces this. No Firestore call should occur without a confirmed `uid`.
10. **Ring math** (`src/lib/ringMath.ts`, pure — no Firestore imports): Activity-ring progress is **uncapped** everywhere (1.42 = 142%; rendering wraps a slightly darker second arc past 100%). Ring goals are **effective-dated and per-day-of-week**: a day is always scored against the goal version active on that day (latest `effectiveFrom <= date`, `createdAt` breaks ties), so editing goals never re-scores history. Period progress is **sum-vs-sum**: Σ actual values ÷ Σ resolved per-day goals over the same range — never average-of-percentages or days-closed; days with no healthMetrics doc contribute 0 to the numerator while their goal still counts in the denominator. To-date periods (current week/month/YTD) never extend past today. "Today's" sleep = `sleep_total_hours` on today's doc (last night's sleep). Ring calculations never write to Firestore.

11. **Settings max HR is the single source of truth for client-side HR math** (product decision, 2026-06-11 audit): every surface that displays or uses a max heart rate — HR zone boundaries (Run Detail Zones card, Personal Insights "Running Intensity by HR Zone"), `TrainingLoadBadge` tooltips, and all live/in-memory training-load estimation — resolves `users/{uid}/settings/prefs.maxHeartRate` via `resolveMaxHr(settings)` (fallback `DEFAULT_MAX_HR = 185` only when unset) and passes the resolved value down. No display or calculation path may hardcode a max HR. Historical **persisted** `trainingLoadV2` values are never recomputed or migrated when the setting changes — only live computation follows the new value. (The iOS write-time pipeline is outside this repo's control; see MEA.)

12. **Date-only strings parse as LOCAL dates**: race (`halfMarathonRaces.raceDate`), plan (`plans.startDate`), and goal (`goals.startDate/endDate`) dates are stored as `"YYYY-MM-DD"` strings and MUST be parsed via `parseLocalDate` / counted via `daysUntil` (`src/utils/dates.ts`). `new Date("YYYY-MM-DD")` parses as UTC midnight, which renders the **previous** calendar day in US timezones and once made the same race show "Sat, Sep 5 · 86 days" on Plan Insights but "Sun, Sep 6 · 87 days" on Races. `daysUntil` counts whole local calendar days (0 = today), so the count never shifts with the time of day. The mirror rule applies to workout **timestamps**: a `healthWorkouts.startDate` Timestamp is bucketed under its **local** calendar day everywhere — `weeklyLoad.ts`, `trainingLoadSeries.ts`, `routePerformance.ts`, `MiniCalendar.tsx`, `services/autoMatch.ts`, and (since the 2026-08-20 session) `matchPlanToActual`. `startDate.toISOString().split("T")[0]` is the UTC day and is wrong for any surface a user reads as "what day did I run" (see §6 #42). The same rule governs a plan's **week windows**: `buildPlanAdherence`, `buildPredictionTrend` (`racePrediction.ts`), and `buildPredictionProjection` (`predictionTrend.ts`) all derive their Mon→Sun range from `parseLocalDate(plan.startDate)`, never `new Date(...)` (see §6 #43, #44). Note `parseLocalDate` accepts a **date-only** string: it returns `Invalid Date` for `"YYYY-MM-DDTHH:mm:ss"`. That is safe in production because `services/plans.ts` normalizes `startDate` to `toDate(...).toISOString().split("T")[0]` on read, but test fixtures must use the date-only form.

## Section 5 — Key Calculations & Business Logic

1. **Pace formatting** (`src/utils/pace.ts`): `formatPace(secPerMile)` rounds total seconds first (`Math.round(secPerMile)`), then extracts minutes/seconds with integer arithmetic. Fixes the "10:60" rounding bug. Same pattern in `formatDuration`.

2. **HR Drift** (`src/utils/metrics.ts`): `((secondHalfAvgHR - firstHalfAvgHR) / firstHalfAvgHR) × 100`. Computed on device; requires ≥20 min or ≥2.0 mi. Thresholds by distance bucket — short (<3 mi): good ≤5%, ok ≤10%; medium (3–6 mi): good ≤7%, ok ≤12%; long (6+ mi): good ≤10%, ok ≤15%.

3. **Cadence** (`src/utils/metrics.ts`): Thresholds — short: good ≥170 spm, ok ≥160; medium: good ≥168, ok ≥158; long: good ≥165, ok ≥155.

4. **Training Load (TRIMP) — LEGACY zone-multiplier model, RETIRED FROM DISPLAY (Prompt 3)** (`src/utils/trainingLoad.ts`): `computeTrainingLoad()` is marked `@deprecated` and is no longer referenced by any display/aggregation path (kept in place, unreferenced, for trivial rollback; remove in a future cleanup). All load surfaces now go through `resolveDisplayLoad()` (see item 4a). Description of the legacy model retained for reference:
   - Formula: `TRIMP = durationMinutes × zoneMultiplier(avgHR) × factor`
   - `DEFAULT_MAX_HR = 185 bpm` fallback. Consumers resolve `users/{uid}/settings/prefs.maxHeartRate` via `resolveMaxHr(settings)` and pass the resolved value into `computeTrainingLoad()`, `buildDailyLoadMap()`, zone-boundary helpers, badges, dashboard/insights summaries, and AI Coach context.
   - Zone multipliers (running zones): Z1 Recovery <60% ×1.0 | Z2 Aerobic 60–70% ×1.5 | Z3 Tempo 70–80% ×2.5 | Z4 Threshold 80–90% ×4.0 | Z5 Max ≥90% ×6.5
   - Strength activities use shifted zone bands (Z5 starts at 80%, not 90%)
   - Post-TRIMP scaling factors: running/cardio = 1.0 | **HIIT/OTF = the session's average HR reserve** (intensity-proportional, `clamp(avg HRR, 0, 1)`; `DEFAULT_HIIT_FACTOR = 0.75` fallback only when avgHR/reserve is unusable) | strength (lifting/cooldown) = 0.25 | mindful (yoga/pilates/barre) = 0.20. Extracted into the shared `activityLoadFactor(activityType, hrr?)` helper (the optional `hrr` is consumed ONLY by the HIIT/OTF branch; running/strength/mindful ignore it) so the legacy and V2 models stay in sync. **HIIT was a flat 0.75**, but validation against Strava RE showed a flat factor cannot fit (easy HIIT wants ~0.62, hard ~0.89, tracking avg %HRR ~1:1); `f = avg HRR` is parameter-free and collapsed mean error from ~15% to ~4% across 6 reference sessions (**small ground-truth sample — relationship + 0.75 fallback are TUNABLE**). HIIT/OTF ONLY: running/strength/mindful factors and the shared `bannisterWeight`/HRR curve are unchanged (runs validate at factor 1.0 on that curve, so steepening it would regress them). For the streamed path the factor uses one per-session scalar (avg HRR from `avgHeartRate`), NOT a per-sample factor — the per-sample integral remains the base load.
   - `STRENGTH_LOAD_FACTOR` was bumped from 0.20 → 0.25 (validated against Strava Relative Effort)
   - `computeTrainingLoad()` returns null when HR or duration is missing/invalid

4a. **Training Load V2 — Banister TRIMP on HR reserve** (`src/utils/trainingLoad.ts`, `computeTrainingLoadV2`): the universal avg-HR baseline that will score ALL runs after the Prompt-3 cutover (a streamed per-second override arrives in a later phase). Additive — the legacy item 4 model is untouched. Math: `HRR = clamp((avgHR − restingHr) / (maxHr − restingHr), 0, 1)`; `weight = 0.64·e^(1.92·HRR)` (Banister male coefficients, a tunable pair); `rawTrimp = durationMinutes · HRR · weight`; `load = round(rawTrimp · TRAINING_LOAD_V2_SCALE · activityLoadFactor)`. Anchors/tunables: `maxHr` via `resolveMaxHr` (fallback `DEFAULT_MAX_HR=185`), `restingHr` via `resolveRestingHr` (fallback `DEFAULT_RESTING_HR=60`), `TRAINING_LOAD_V2_SCALE=1.14` (anchored so validated reference runs ≈ Strava Relative Effort). Returns null (never 0) when avgHR is missing/invalid, duration ≤ 0, or `maxHr ≤ restingHr` (divide-by-zero guard).    - **Streamed integral** (`computeStreamedTrainingLoad`): a precision OVERRIDE for dense-HR runs **and HIIT-style hrStream workouts** that integrates the Banister weighting over every consecutive per-point timestamp pair instead of using one whole-run HRR. `hrCoverage` = points-with-finite-hr / total; if `hrCoverage < STREAMED_HR_COVERAGE_MIN=0.5` or `< 2` points it falls back to the avg-HR model (`method: "avg-hr-fallback"`). Per step: `dt = t[i+1]−t[i]`; `dt ≤ 0` skipped; `dt > TRAINING_LOAD_DT_CLAMP_SEC=10` is **clamped** (pause/auto-pause gaps still count, capped — not dropped); `hr` carries forward the last valid sample; `rawStep = (dt/60)·hrr·bannisterWeight(hrr)`. Reuses the SAME `bannisterWeight` / `TRAINING_LOAD_V2_SCALE` / `activityLoadFactor` as the avg-HR model (no duplicated constants). A clean ~1 Hz stream reconciles with the avg-HR result within ~5% for steady efforts, but **spiky HIIT reads materially higher** — `hrr·bannisterWeight(hrr)` is convex, so the per-sample integral credits time at HR spikes that a whole-run average flattens away (this convexity gain is the motivation for consuming `hrStream`). 7. **Riegel race prediction** (`src/utils/riegelFit.ts`): Weighted WLS regression in log-log space: `ln(time) = a + k × ln(distance)`. Recency: 5-week half-life (0.5^(days/35)). Tier weights: RACE=3.0, QUALITY=1.75, BASELINE=1.0, PLANNED=1.0, PLANNED_QUALITY=1.75 (synthetic future-run efforts — §7c; PLANNED gets no boost, decay still applies; PLANNED_QUALITY matches real QUALITY — see §7c for pace-derived detection). Individual weights normalized then capped at 5.0. Half marathon gate: ≥4 efforts + 2+ medium-long runs (≥4 mi in last 35 days) + longest ≥6 mi — bypassed when a RACE-tier anchor ≥ target distance exists. Sanity filters: pace 4:30–15:00/mi, ≥0.5 mi, ≥5 min. **`asOf` parameter** (`buildQualifyingEfforts({ asOf })`, default = wall-clock now): the reference date for BOTH the lookback windows (56d ordinary / 120d race) AND each effort's `ageDays` (which drives the recency decay). Runs after `asOf` are excluded. Passing a past `asOf` recomputes a prediction "as of" that date with the SAME model — weights, k-clamp, decay formula are unchanged; only the reference date moves (`asOf=now` reproduces the prior value exactly). The Plan Insights card and the weekly trend both go through the shared pure `predictRaceTime(runs, params, asOf)` (`src/utils/racePrediction.ts`) so they can never diverge.

7a. **Weekly prediction trend** (`buildPredictionTrend`, `src/utils/racePrediction.ts`): for each plan week, calls `predictRaceTime` with `asOf` = that week's END (Mon-start + 6d, end-of-day — the SAME boundaries `buildPlanAdherence` uses, so the trend lines up week-for-week with the adherence charts). 7b. **HR-gated best-effort projection** (`src/utils/bestEffortExtraction.ts`, folded into `predictRaceTime` via `RacePredictionParams.bestEffortSegments`): the base fit (item 7) is dominated by easy training runs, so its half prediction reflects *easy-run* pace, not *race-effort* pace. This adds the genuine race-gear efforts hiding in the data as high-weight efforts ALONGSIDE the base runs (base remains corroboration; no base run is removed). Pipeline: (1) **extract** — for each recent run (`BEST_EFFORT_RECENCY_DAYS=56`d window) emit a `full-run` effort when its run-level avg HR clears the gate (`HRR_GATE_THRESHOLD=0.80` %HRR, anchors from `settings/prefs`, **never hardcoded**), plus the fastest `continuous-segment` per window `[3,5,8]`mi whose own per-mile HR clears the gate (pace from the GPS `route` subcollection — `mileSplits` has no pace field — with each segment's GPS-haversine distance reconciled to recorded `distanceMiles`, since GPS under-counts ~3%), plus one `fast-finish` segment — the **longest contiguous stretch of miles that EACH clear the gate individually** (`bestFastFinishSegment`, same route-derived pace + GPS reconciliation), which rescues an easy-start / hard-finish run whose whole-run avg HR fails the gate but whose finishing miles pass it (the `continuous-segment` path can't: it gates on the window's *average* HR, which the easy start washes out); (2) **select ceiling** (`selectCeilingEfforts`) — keep the fastest effort(s) per distance bucket, with **two distinct floors AND two distinct keep-counts**: `full-run`/`continuous-segment` keep the **≥5mi** floor and strict single-winner-per-bucket (short fast efforts steepen `k` and bias the half slow; "hard but slow" segments are dropped), while `fast-finish` segments use their own **≥`FAST_FINISH_MIN_SEGMENT_MILES`=2mi** floor AND keep the **top `FAST_FINISH_CEILING_TOP_N`=3** per bucket by pace (not winner-take-all — a run whose fast finish genuinely clears every gate isn't shut out just because another run's fast finish at the same rounded distance is marginally faster; both are legitimate race-gear evidence, e.g. two independent runs both producing a genuine ~2mi hard finish a few % apart in pace); all candidates (full-run/continuous-segment single winner + fast-finish top-3) are then merged into buckets by rounded distance and re-capped at `FAST_FINISH_CEILING_TOP_N` per bucket so a fast-finish group and a full-run at the same distance still can't all double-count; (3) **project** (`projectPaceToRaceEffort`) — nudge each sub-target segment's pace faster ∝ its HRR shortfall below `RACE_EFFORT_HRR_TARGET=0.90`, clamped at `MAX_PACE_ADJUSTMENT_PCT=0.06`; (4) **weight** — feed at `tier=QUALITY` with `EffortPoint.weightMultiplier=BEST_EFFORT_WEIGHT_MULTIPLIER=6` so they are the primary signal (k-clamp `[1.04,1.10]` UNCHANGED). `predictRaceTime` ages/filters segments relative to `asOf`, so the live card and weekly trend stay consistent. **Invisible in the UI** — the prediction renders through the existing card unchanged. **`RACE_EFFORT_HRR_TARGET=0.90` is the one design assumption** (assumes a 90% avg race HRR — above this athlete's *demonstrated* 80–84% on hard long runs — so the number is a race-effort PROJECTION, not a demonstrated time; 0.85→~2:14, 0.90→~2:11 on the current dataset). **Live wiring** (half+ targets only): both the Plan Insights card/trend AND the Run Detail **This Run's Impact** tile now hydrate `mileSplits` for the recency-window runs via `hydrateFastFinishSplits` (`src/services/fastFinishSplits.ts`) before building segments, so `fast-finish` (and `continuous-segment`) credit is live on both surfaces. **Cost guard** — the expensive GPS `route` read is spent only on runs that pass a **cheap pre-filter**: `hydrateFastFinishSplits` first reads the lightweight `mileSplits` subcollection (per-mile `avgBpm`, no route) and fetches `route` (via the memoized `getRoutePoints` cache) only when at least one mile already clears the gate by `avgBpm` alone (`fastFinishPrefilterBpm` = `restingHr + 0.80·(maxHr−restingHr)` = **153bpm** at 175/65). Runs whose every mile is below the gate skip the route read entirely; per-mile pace is derived with the same `computeMileSplits` haversine used by the run-detail splits table. Both surfaces build segments through the shared `buildBestEffortSegments(runs, asOf, maxHr, restingHr)` recipe (so they never diverge). The tile's `computeRunImpact` (`src/utils/runImpact.ts`) rebuilds segments PER-SET (with vs. without the viewed run), so excluding the run drops it from BOTH the base fit AND the best-effort ceiling; it reports `affectsProjection=false` for runs outside the fit window (<3mi or older than the recency window) so the tile shows "doesn't affect your current projection" rather than a misleading 0. **Known gap:** a fast-finish segment is always <3mi by construction and is therefore silently discarded by `fitRiegel`'s `minMilesForFit=3.0` for half-marathon+ targets before the regression ever runs — the ceiling selection above (single winner, then top-3) currently has NO effect on any half+ prediction. A bypass was attempted and reverted after real-data testing showed oversized swings — see §6 #28's Follow-up #3 for the full history and why a weighting redesign is needed before retrying.

7c. **Plan-completion projection** (`buildPredictionProjection`, `src/utils/predictionTrend.ts`): a dashed line that extends the §7a trend from the current week to race day, showing where the predicted finish is headed **if the plan is completed as written**. For each FUTURE plan week (Monday > now) up to race day, it re-runs the SAME `predictRaceTime` with `asOf` = that week's end (capped at race day for the terminal point), passing synthetic PLANNED-tier efforts via the new `RacePredictionParams.extraEfforts` hook: every remaining planned run scheduled on/before that week's `asOf` is converted by `planEntryToSyntheticEffort(entry, performedDate, asOf, planEasyPaceSecPerMile)` (`src/utils/riegelFit.ts`) into an `EffortPoint` (distance × target pace → time; `ageDays` relative to that week's `asOf`; `isTreadmill` from `runType`). **Quality detection (pace-derived):** `workoutType` is `undefined` on live plan entries, so tier can't be read off that field. `planEasyPaceSecPerMile` — the median target pace across the plan's non-rest, non-`longRun` entries (`computePlanEasyPaceBaseline`, computed ONCE per plan, stable across every projected week, not recomputed per-week) — is compared against each entry's own target pace: an entry beating the baseline by ≥`PLANNED_QUALITY_PACE_THRESHOLD_SEC_PER_MILE=30` s/mi is tagged `PLANNED_QUALITY` (weight ×1.75, matches real QUALITY); everything else (including long runs, and every entry when the baseline is `null` — fewer than 3 qualifying entries) is tagged `PLANNED` (weight ×1, unchanged). The 30s/mi threshold is a judgment call, not derived — tune from production QA. `workoutType` backfill (to make detection type-derived instead of pace-derived) is a known follow-up, not yet implemented. **Blended, not plan-only:** the real quality/race efforts already in the historical set keep informing each future fit through the model's existing 120-day memory + 5-week half-life decay (they simply age as `asOf` marches forward) — no new carry-forward logic — while the mostly-easy planned runs add volume. Synthetic efforts are appended AFTER `buildQualifyingEfforts` (never passed through it), so they can never be upgraded to QUALITY and are never HR-gated. **Empty projection** (chart falls back to the §7a line only, no dashed segment) when: no active plan, no linked race distance, the race is in the past, or no remaining plannable run entries (rest days / zero-distance / no-pace entries don't count) fall between today and race day. `extraEfforts` absent/empty ⇒ `predictRaceTime` is byte-for-byte identical to before, so the live card and historical trend are unaffected. Pure / in-memory — no Firestore, no new storage. Rendered as a third dashed series in `PredictionTrendChart` (same primary color as the predicted line, `strokeDasharray`, bridged to the last real point; X-axis reuses the §7a `W{n}` week labels).

**⚠️ `buildPredictionProjection` is a SIGNAL generator, not the displayed series — it is anchored before rendering.** On its own the raw projection trends *monotonically slower* toward race day: synthetic PLANNED efforts stay perpetually fresh (aged relative to each future week's `asOf`, so `ageDays` is always small) and *accumulate* week over week, while the one strong real signal — the RACE anchor — decays away as `asOf` marches forward (by race week a single easy planned run outweighs the real race result ~1.76×; planned mass in aggregate ~20×), dragging the fit's intercept `a` toward easy pace (k stays ~1.078, inside the clamp — the clamp is *not* the cause). **`buildAnchoredPredictionProjection` (same file) is what the chart renders.** It anchors to TODAY'S live prediction — `liveBaselineSeconds`, the exact `predictRaceTime(...).predictedSeconds` shown on the card (asOf = now, best-effort segments included; the page computes it once as `livePrediction` and derives both `raceFit` and this from it, so card and projection can't diverge) — and lets the raw signal apply only a *bounded* nudge: `projectedSeconds = liveBaselineSeconds × (1 + clamp(rawDeltaPct, ±MAX_PROJECTION_ADJUSTMENT_PCT))`, where `rawDeltaPct` is the raw signal's proportional move from its own week-0 (today) value. The raw week-0 value is `predictRaceTime` at `asOf = today` (no planned entries have occurred yet, so it equals `liveBaselineSeconds` by construction — same call); it is used only as the internal reference for measuring direction, never displayed. This keeps the plan's DIRECTION and MAGNITUDE as a real signal (a quality-heavy block nudges down; a taper nudges up) while capping drift. **`MAX_PROJECTION_ADJUSTMENT_PCT = 0.04`** (exported from `predictionTrend.ts`) is a **judgment call, not a derived value** — ±4% ≈ ±5:15 on a 2:11 half; too tight looks flat/uninformative, too loose lets the raw bug shape creep back — tune from production QA. `buildAnchoredPredictionProjection` returns `[]` (chart shows the §7a line only, unchanged empty-state) when `liveBaselineSeconds` is null (card has no prediction), today's raw fit is insufficient, or the raw signal is empty. `MAX_PROJECTION_ADJUSTMENT_PCT` affects ONLY the anchored projection — never the historical trend line, the live card, or the raw signal function.

12. **Grade Adjusted Pace (GAP)** (`src/utils/gradeAdjustedPace.ts`): **GAP is now RATIO-BASED** — the run-level KPI = `avgPaceSecPerMile × (1 / aggregateFactor)`, i.e. the trusted device pace scaled by a unitless grade ratio. This fixes a systematic GAP-slower-than-pace bug on net-gain runs caused by three issues: (#1) **basis mismatch** — the displayed Pace KPI is the device `avgPaceSecPerMile`, but GAP was previously recomputed on GPS 2D-haversine distance (which runs shorter than device distance → GAP slower even on flat ground); (#2) **Jensen convexity** — summing per-segment `1/factor` over symmetric rolling terrain inflates GAP slow (1/factor is convex); (#3) **dead-band** — the ±1.5% dead-band zeroed gentle sustained net climbs (avg grade often sub-1.5%). The `aggregateFactor` is ONE Minetti factor (`gradeAdjustmentFactor`, Minetti et al. 2002, grade clamped ±30%, floored 0.1) computed from the run's **net smoothed elevation change over total moving horizontal distance** — so symmetric rolling (net ≈ 0) yields ratio ≈ 1 (no slow-bias) and flat ground gives GAP == displayed Pace exactly, while net-uphill → faster and net-downhill → slower. Inputs preserved: 11-point centered altitude smoothing (`ALT_SMOOTHING_WINDOW=11`), the 25 m resampled baseline (`GRADE_BASELINE_METERS=25`), and the ±1.5% dead-band (`GRADE_DEADBAND_PERCENT=1.5`) — but the dead-band now applies **only to per-span noise rejection feeding the chart/table series**, NOT to the run-level aggregate grade. **Moving time/distance** are derived from route points (a segment is moving only if it covers ≥`MIN_MOVING_DIST_M=1.0` m at ≥`MIN_MOVING_SPEED_MS=0.5` m/s); the GPS-derived per-point and per-mile GAP series are scaled by a single basis-correction (`avgPaceSecPerMile / gpsRawMovingPace`) so they read consistently with the KPI. When `avgPaceSecPerMile` is null, the basis falls back to GPS raw moving pace. `computeRunGap(points, totalDistanceMiles, movingTimeSec, avgPaceSecPerMile?)` also returns `netRiseM` (NET elevation change in meters, end−start, endpoint-averaged; null when no geometry) for the Run Detail elevation KPI. **Net-grade hardening:** (a) the net rise is averaged over the first/last `NET_GRADE_ENDPOINT_SAMPLES=5` moving points' smoothed altitudes (single-endpoint fallback when fewer than 2× that many moving points), so one noisy first/last GPS sample can't tilt the whole-run net; (b) a tight aggregate-grade dead-band `AGGREGATE_GRADE_DEADBAND_PERCENT=0.10` snaps pure endpoint-noise jitter (|net grade| ≤ 0.10%) to flat (GAP == pace) while leaving real shallow descents intact (e.g. the −0.229% reference run stays ~+7 sec slower). **0.10% is a tunable** (measured real-vs-noise endpoint variance ≈ 0.02%, well below it).

13. **Goal progress** (`src/utils/goalProgress.ts`): `computeGoalProgress(goal, runs, today) → GoalProgress`. Status by date range: `upcoming` (today < startDate) / `active` / `completed` (today > endDate). `actual` sums each in-range run's `distanceMiles` (distance), `durationSeconds` (time), or +1 (count). Pace status (active only): `ahead` when actual ≥ 102% of expected linear pace (`target × daysElapsed/daysTotal`), `behind` when ≤ 98%, else `on_track`; completed goals report met/missed via `percent`. Nulls are preserved (window with no finite values → null) so line breaks survive; falls back to a fixed-count window when timestamps are unusable. Used to smooth the pace and GAP display series in `RunOverlayChart` (applied at full route resolution, after outlier-nulling; underlying GAP/per-mile values untouched), and to lightly smooth the **elevation** Area (`ELEV_SMOOTH_WINDOW_SEC=20`, display-only — the Total Ascent KPI still reads the device `elevationGainM`, not this). **Overlay chart default series:** the chart opens showing only **Pace + Elevation** (both always-on); **GAP and HR are opt-in** via two in-header pill toggles (`showGap`/`showHr`, both default OFF — in-memory only, reset on every remount/page load, never persisted to Firestore/localStorage/settings; the HR pill is disabled when the run has no per-point HR, alongside the existing "Per-point HR not available" note). **Smoothing precedes decimation:** outlier-nulling, the pace-axis domain, and `rollingAverage` all run on the full-resolution (~1Hz) route array; only the already-smoothed series is then strided down to `MAX_CHART_POINTS=200` for render. Decimating first (the prior order) left rendered points ~`duration/200`s apart, which collapsed the 25s/60s/20s windows to ~1 sample on runs longer than ~42min — the moving average became a no-op and raw GPS jitter rendered unchanged. Sampling an already-smooth curve stays smooth at any run length at no extra render cost; short runs (≤~3min, no decimation) are unaffected.

16a. **`weeksHitTarget` vs. `completedRuns` — two INDEPENDENT metrics that are EXPECTED to disagree (not a bug).** Both live in `buildPlanAdherence` (`src/utils/planAdherence.ts`) and are shown side by side on `/plan-insights` and `PlanCompletionSummary`, which makes them look like two views of one number. They are not. **`weeksHitTarget`** is an **aggregate weekly-VOLUME** check: `weeks.filter(w => w.plannedMiles > 0 && w.actualMiles >= w.plannedMiles * 0.85).length`. Its `actualMiles` is the week's TOTAL run mileage in the Mon→Sun local window — matched runs **plus bonus/unplanned runs** (§5.25) — compared against the sum of the week's planned entry distances. It knows nothing about which planned session produced which mile. **`completedRuns`** is a **per-entry EXECUTION** count: for each non-rest entry, `isPlanEntryCompleted(statusForRunEntry(plan, e, matchMap))` (§6 #39) — i.e. the entry got a same-day/±1-day match of ANY quality, `"met"` or `"partial"`. It knows nothing about how many miles the week totalled; a bonus run cannot complete an entry, and a hugely-over-distance run completes exactly one. The 0.85 constants in the two are also unrelated: `weeksHitTarget`'s is a WEEK-level mileage-sum ratio, while match quality's `COMPLETION_THRESHOLD_RATIO` (§5.6, §6 #29) is an ENTRY-level ratio — and since partial matches count as completed, the entry-level ratio does not gate `completedRuns` at all. **Do not "reconcile" them, derive one from the other, or file their disagreement as a defect** — a per-run tile reading `4 / 4 runs` next to a week that missed its mileage target is correct output.

    **Divergence directions, with real data.** Verified read-only against the local snapshot (`scripts/snapshots/training-web-snapshot.json`, exported 2026-07-24) over this user's three running plans, restricted to plan weeks fully elapsed as of that export: the two metrics disagreed on **8 of 32** weeks (25%) — and the two Sept-2026 half plans share most of their early weeks, so the distinct underlying weeks are fewer. Both directions occur, and each has a plain training explanation:

    - **Every run done, mileage target missed** (`hitTarget=false`, `completedRuns === plannedRuns`) — *"Half Marathon — Sept 20, 2026 (Sub 9:09)", W7, Mon 2026-06-29 → Sun 2026-07-05*: all four planned entries matched (`4 / 4` completed — Mon 3mi→2.88, Wed 5mi→4.57, Fri 5mi→4.89 all `"met"`, plus Sat's 10mi long run matched at 6.30mi as `"partial"`), yet the week totalled **18.6 of 23.0 planned miles (81%)** → below the 85% line, so the week does NOT count toward `weeksHitTarget`. Nothing was skipped; the long run was cut short, and one short long-run is enough to sink a weekly total while leaving per-run completion perfect.
    - **A run skipped, mileage target still hit** (`hitTarget=true`, `completedRuns < plannedRuns`) — *"Half Marathon — Spring 2026", W2, Mon 2026-01-26 → Sun 2026-02-01*: Monday's 2mi easy entry never got a run (`"missed"`, `3 / 4` completed), but an unplanned **3.30mi bonus run on Thu 2026-01-29** plus slightly-long executions of the other three put the week at **12.1 of 10.8 planned miles (113%)** → the week DOES count toward `weeksHitTarget`. Same plan, W5 (2026-02-16 → 02-22) is the same shape with a shortfall instead of a surplus: Friday's 1.75mi entry missed (`3 / 4`), week at 13.7 / 15.4 = **89%**, still ≥85% and still counted.

    **Which to read when**: `weeksHitTarget` answers *"did the training volume land?"* and is the input to the adherence % on the Plan Insights card and to §7d's consistency credit. `completedRuns` answers *"did the prescribed sessions actually get run?"* and is what the "X / Y runs" tile, the week-progress bars, and the plan calendar report. A plan can score well on one and poorly on the other, and the gap between them is itself the signal (all-runs-done-but-short = systematic under-distancing; target-hit-but-runs-missed = mileage being made up off-plan).

16. **Pace-by-distance trend** (`src/lib/paceRangeTrend.ts`): `computePaceRangeTrend(runs, minMiles, maxMiles, window, now)` originally powered the Personal Insights "Pace by distance" section (**now merged into Run Analysis, §5.27** — the section was retired, but this module is retained: it exports `granularityForWindow`/`windowStartDate`/`periodStartFor`/`labelFor` and the `MIN_VALID_PACE`/`MAX_VALID_PACE` bounds that `runAnalysisTrend.ts` reuses, and `computePaceRangeTrend` still backs the parity tests). Granularity: `1m/2m/3m → week` (Monday-start via `weekStart`), `6m/12m/ytd → month` (month-start computed inline). `windowStartDate`: `ytd → Jan 1 of now's year`, `Nm → now minus N calendar months`. 17. **Best Efforts** (`src/utils/bestEfforts.ts`): `computeBestEfforts(points)` computes each run's fastest continuous elapsed-time segment for `1mi`, `5k`, `10k`, `10mi`, and `half`. It builds cumulative 2D haversine distance and elapsed-time arrays from route points, then uses an O(n) two-pointer sliding window per target distance. The right boundary is linearly interpolated when the window overshoots the target distance (`t = t0 + ((D - d0) / (d1 - d0)) * (t1 - t0)`) so results represent exactly the standard distance, not the next sampled route point. Stopped/micro-pause time is intentionally included, matching Strava-style elapsed best efforts; GAP's moving-time stop filtering is not used here. Runs shorter than a target distance store `null` for that key. The persisted `1mi` value also MUST pass the shared strict validity window `180 < seconds < 1200`; `computeBestEfforts` converts any non-finite, boundary-equal, near-zero, or over-limit result to `null` before any caller can persist it, while aggregation repeats the same predicate as defense in depth. Results are persisted on `users/{uid}/healthWorkouts/{workoutId}.bestEfforts` with `computedFromRouteComplete`, `computedFromPointCount`, and `computationVersion`; Run Detail recomputes when the field is absent, a partial basis becomes complete, or the version is stale. The persistence guard is computation version 2, so version-1 documents self-heal on their next eligible route read. `scripts/repairBestEffortsFreshness.ts` dry-runs then repairs legacy/stale complete-route documents. Personal Insights' current-year fastest-mile stat reads the persisted parent-doc `bestEfforts["1mi"]`, keeps the same validity window, restores local-calendar-year filtering, and never falls back to raw routes.

20. **Shoe replacement projection** (`src/utils/shoeProjection.ts`): `projectShoeReplacement({ currentMiles, limit }, shoeRuns, now?)` estimates a shoe's remaining life from its RECENT rate. `recentMilesPerWeek` = (Σ miles of that shoe's runs within the last 28 days, boundary-inclusive at 28-days-ago, future runs excluded) ÷ 4. `milesRemaining = max(limit − currentMiles, 0)`. State machine: `currentMiles ≥ limit` → **"over"** (projectedDate null); else `recentMilesPerWeek ≤ 0` → **"inactive"** (projectedDate null — no divide-by-zero, never a bogus "never"); else `projectedDate = now + (milesRemaining / recentMilesPerWeek)·7 days` with state **"approaching"** when `currentMiles/limit ≥ 0.75` else **"ok"**. Returns `null` when no positive limit is set (no retirement target → nothing to project; the card omits the line). Pure / in-memory — `currentMiles` = `totalMileage` (startMileageOffset + assigned-run miles), `shoeRuns` derived from `shoeAssignedRuns`; no Firestore, no storage, no input mutation. The Shoes page renders one compact line under each card's mileage bar (`--caution`/`text-warning` when approaching, `--negative`/`text-danger` when over).

21. **Week Score + breakdown** (`src/utils/weekScore.ts`): `computeWeekScore(input)` is a weighted sum of three components, each `round(adherence × maxPoints)`, **pro-rated against the plan scheduled THROUGH TODAY** (not the full week) so an on-track mid-week reads as on-track instead of "incomplete". Inputs carry a `daysElapsed` (Monday-start → today inclusive, today = a full day, clamped 0..7; a fully-elapsed past week = 7, a future week = 0). Components: **Run miles** (`RUN_MAX_POINTS=40`, `min(actualToDate/plannedMilesThroughToday,1)`), **Training load** (`LOAD_MAX_POINTS=35`, `min(loadToDate/proRatedLoadTarget, LOAD_FULL_CREDIT_RATIO=1.2)/1.2` — full credit at 120% of the pro-rated baseline), **Workouts** (`WORKOUT_MAX_POINTS=25`, `min(completedToDate/sessionsScheduledThroughToday,1)`). **Pro-rating denominators**: planned-mile and session denominators sum only plan entries whose `weekday ≤ daysElapsed` (`isScheduledThroughToday`, computed at the page level from each plan week's entries); the load target is `proRatedLoadTarget(avgWeeklyLoad, daysElapsed) = avgWeeklyLoad × (daysElapsed/7)` — there is **no per-day planned load** in plan data, so this linear fraction of the 28-day weekly baseline is the load denominator. **Zero-denominator rule**: nothing scheduled through today for a component (rest day, future week, absent plan, or zero baseline) ⇒ that component scores **100%** so the card never looks "behind" for targets not yet due. Weights/caps/bands are unchanged from the prior full-week version; on the last day (`daysElapsed=7`) the pro-rated score equals the old full-week score by construction. `total = runScore + loadScore + workoutScore` (0–100). The This Week card adds a small `basisLine` subtext stating the basis (e.g. "vs plan through Wed" / "vs full-week plan" / "Upcoming week") and renders the additive, collapsed-by-default "How is this calculated?" disclosure. RUN_TYPE_LABELS[runType] ?? "Run"` — `PlannedRunEntry` has **no `label` field**), `findActiveRunningPlan(plans)` picks the one `status:"active"` running plan, and `buildRunTitleMap(plan, workouts)` **inverts** `matchPlanToActual` (entry→run) into a memoizable `workoutId → {label, distanceMiles}` map so a render loop does an O(1) lookup without re-running the (date+distance) matcher per row. 26. **Per-run Efficiency Score + %HRR-adjusted baseline + trend/buckets** (`src/utils/efficiencyScore.ts`, pure — NO Firestore reads/writes; scores an already-fetched, single-uid workouts array): scores a run's pace-relative-to-HR effort against the runner's OWN rolling baseline, adjusted for the effort level the run was actually run at. **Efficiency Factor** `EF = (3600/avgPaceSecPerMile) / avgHeartRate` (mph per bpm; higher = more speed per heartbeat). **Effort** is `%HR-reserve` (Karvonen) via the shared `computeHRReserve(avgHeartRate, restingHr, maxHr)` helper (`src/utils/hrReserve.ts`, mirrors the Training Load V2 inline formula) — HR anchors come from resolved user settings (`resolveMaxHr`/`resolveRestingHr`, defaults 185/60), the SAME source Training Load uses; callers pass them in, never a new prefs fetch. **Baseline** (`buildEfficiencyBaseline(workouts, asOfDate, restingHr, maxHr, windowDays=60)`): over the trailing window `[asOfDate − windowDays, asOfDate)` (**date-anchored to the scored run, never `Date.now()`**), averages EF + cadence and, when `runCount ≥ MIN_BASELINE_RUNS=5` AND the %HRR spread `hrrMax − hrrMin ≥ MIN_HRR_RANGE_FOR_REGRESSION=0.08`, fits an OLS **regression of EF on %HRR**; below either gate `regression` is null and the flat average EF is used. The old BASELINE/QUALITY/RACE **tier split and the riegelFit `buildQualifyingEfforts` dependency are removed entirely**. **Score** (`computeEfficiencyScore`): `expectedEF` = regression `intercept + slope·clamp(runHrr, hrrMin, hrrMax)` when fitted (`usedRegression:true`), else `baseline.avgEF`; `percentDelta = (runEF − expectedEF)/expectedEF`; `score = clamp(50 + (percentDelta/SCORE_SCALE_PCT)·50, 0, 100)` (50 = neutral), plus the optional cadence modifier `clamp(cadenceDelta/CADENCE_SCALE_PCT, ±1)·CADENCE_MODIFIER_MAX_POINTS=5`. Result also carries `hrrPct` (0–100 int) and `usedRegression`. Returns `status:'building_baseline'` (null score, excluded from all aggregates) when the baseline has `< MIN_BASELINE_RUNS` EF-backed runs or the run lacks pace/HR. **`scoreWorkoutsEfficiency(workouts, restingHr, maxHr, windowDays=60)`** builds each run its OWN self-excluding, date-anchored baseline (runs strictly before that run) and returns `Map<workoutId, EfficiencyScoreResult>` — so a run's score is **stable regardless of newer runs** (the prior "anchored to today" drift bug is fixed). **Weekly trend** (`buildEfficiencyTrend(workouts, restingHr, maxHr, windowDays=EFFICIENCY_TREND_WINDOW_DAYS=112)` = 16 weeks) and **distance buckets** (`buildDistanceBucketSummary(workouts, restingHr, maxHr, windowDays=EFFICIENCY_BUCKET_WINDOW_DAYS=90)`) both score via `scoreWorkoutsEfficiency` (each run date-anchored); trend averages scored-run `score` into Monday-start weeks (shared `weekStart`, local-ISO keys per invariant #12) emitting every week with zero-scored weeks as `avgScore: null` (chart gap, `connectNulls={false}`); buckets average `percentDeltaVsBaseline` (NOT raw score) — short `<5`mi, mid `5 ≤ d < 10`, long `≥10` (5.0 → mid, 10.0 → long), always `[short, mid, long]`, empty → null. Both exclude `building_baseline` runs. **Surfaces**: per-run `EfficiencyScoreBadge` (`{result, baselineRunCount}`; tooltip shows delta, `hrrPct` as "Effort: N% HRR", and "(effort-adjusted)" when `usedRegression`) on Runs list + Run Detail. **The standalone `EfficiencyTrendSection` was removed** — its weekly-average trend is now the **`efficiencyScore` metric of Run Analysis** (§5.27, via `scoreWorkoutsEfficiency`); `buildEfficiencyTrend`/`buildDistanceBucketSummary` remain in `efficiencyScore.ts` (tested, no live caller). **All windows (60/112/90 d), score-band thresholds (65/35), `SCORE_SCALE_PCT=0.15`, `CADENCE_SCALE_PCT=0.05`, `CADENCE_MODIFIER_MAX_POINTS=5`, `MIN_HRR_RANGE_FOR_REGRESSION=0.08`, and the baseline/cadence run-count minimums are TUNABLES** pending calibration. All computation runs client-side over the already-fetched `AppDataContext.workouts` array.

27. **Run Analysis merged metric trend** (`src/lib/runAnalysisTrend.ts`, pure — NO Firestore; consumes an already-fetched runs array): `buildRunAnalysisTrend(workouts, metric, minMiles, maxMiles, windowKey, restingHr, maxHr, now?)` generalizes the retired "Pace by distance" bucketing to **five selectable metrics** — `'pace' | 'cadence' | 'efficiencyScore' | 'load' | 'heartRate'` — returning `RunAnalysisPoint[]` (`{bucketLabel, bucketStartDate, value, runCount}`). Runs are filtered to `[minMiles, maxMiles]` inclusive by **total** distance and to the trailing window, then bucketed via `paceRangeTrend`'s exact `granularityForWindow`/`windowStartDate`/`periodStartFor`/`labelFor` (weekly 1m/2m/3m, monthly 6m/12m/ytd). Per-bucket `value` is a **(value, weight) weighted mean**: **pace** derives `durationSeconds/distanceMiles` weighted by `distanceMiles` (so a bucket = `sum(durationSeconds)/sum(distanceMiles)`, matching `computePaceRangeTrend`) and applies the SAME `[MIN_VALID_PACE, MAX_VALID_PACE]` = `[180,1200]` sec/mi outlier guard (pace-only); **cadence/heartRate** average their field ignoring null; **load** averages `computeTrainingLoadV2` per run (null-load runs skipped); **efficiencyScore** averages `scoreWorkoutsEfficiency`'s `score` over `'scored'` runs only (`'building_baseline'` excluded, never 0), scored ONCE over the full population before bucketing. A bucket with zero qualifying runs → `value: null` (chart gap, never a false 0). `runCount` is **metric-agnostic** (all distance+window-matched runs, regardless of whether the metric was computable). **Surface**: `RunAnalysisSection.tsx` (Personal Insights → Race Readiness, lazy-loaded, replaces Pace by Distance in-place) — metric pills, 1m–YTD window pills, Short[0,5]/Mid[5,10]/Long[10,15] quick-filters (active only on exact range match) + the 0–15 mi dual-handle slider (default `[3,5]`), a headline summary (avg + first-to-last delta "vs start of range"), and a Recharts line with the y-axis **reversed only for pace** and `connectNulls={false}`. **Metric selection is MULTI-select, capped at `MAX_SELECTED_METRICS`=2** (`selectedMetrics: RunAnalysisMetric[]`, default `['pace']`): click order IS slot assignment — `[0]` is primary (left axis, `--color-chart-primary`), `[1]` is secondary (right axis, `--color-chart-secondary`). Both rejection paths are **no-ops returning the previous array unchanged** (so React bails out and the filter-reset effect does not fire): deselecting the LAST remaining metric, and selecting a THIRD while two are active (**no auto-swap** of the oldest pick). At the cap the refusal is **shown, not silent** — every unselected pill dims (`opacity-40` + `cursor-not-allowed` + `aria-disabled`, and the hover colour-shift is dropped) so a blocked pill does not appear to swallow the click; dimming is opacity over the SAME inactive styling rather than a new colour, so it needs no per-theme handling. Selected pills are **never** dimmed (deselecting stays live, so the cap is always escapable), and `onClick` stays attached rather than being conditionally removed — the cap guard lives only in `toggleMetric`. The deselect-the-last-one refusal remains silent and unsignposted. Active pills wear their own series color, which is what makes a chart legend unnecessary; each selected metric also gets its own headline line prefixed by a matching color dot. `buildRunAnalysisTrend` is called **once per selected metric** with a **single `now` computed per render and passed explicitly to every call** (two defaulted `new Date()`s could straddle a period boundary and yield misaligned bucket sets). Results merge into `RunAnalysisComparePoint` — `{bucketLabel, bucketStartDate, primaryValue, secondaryValue, runCount}` — keyed by `bucketStartDate` via a Map rather than zipped by index (bucketing is metric-independent so the arrays ARE aligned, but the Map is correct by construction). `runCount` is a **single shared field, not one per metric**, since it is metric-agnostic. The empty-state gate reads the **primary series only**, so a sparse second metric can never blank a chart that was rendering. The reversed-axis caption keys on pace being on **either** axis. `reversed`/`domain`/`tickFormatter`/`width` follow the **metric, not the slot** (pace formats M:SS and reverses even when it is the right-hand axis) — Recharts supports an independent `reversed` per `YAxis`, precedent in `RunOverlayChart.tsx`. With one metric selected the chart renders exactly as before — a single `<YAxis>`/`<Line>` with **no `yAxisId` prop present at all** (spread of a conditional object, never `undefined`). **Responsive secondary axis**: below `md` (768px, via the new `useIsDesktop`/`useMediaQuery` hook in `src/hooks/useMediaQuery.ts`) the secondary axis renders `tick={false} width={0}` — Recharts then stops *painting* the axis group but still resolves its scale, so the secondary line and its dots plot identically while ~40px of a ~270px mobile plot is reclaimed; the colored line plus its own headline stat still carry the value. The hook starts `false` on the server AND on the client's first render so hydration cannot mismatch (it is progressive enhancement, not load-bearing) — Recharts renders ticks as raw SVG `<text>`, which Tailwind responsive classes cannot target per-element, so the breakpoint must reach it as a prop. Page maps `HealthWorkout` runs to `RunAnalysisWorkout` (`startDate.toISOString()` becomes `date`) in a page-level memo. **Click-to-expand drill-down**: `runsInBucket(workouts, bucketStartDate, window, minMiles, maxMiles, now?)` returns the individual runs behind one chart bucket, reusing `buildRunAnalysisTrend`'s **exact** membership predicate (distance in `[minMiles, maxMiles]` inclusive, parseable date ≥ the trailing-window start, matching period start), so its length always equals that bucket's `runCount`. Metric validity is deliberately **not** applied — a run excluded from the bucket AVERAGE (missing HR, an out-of-`[180,1200]` derived pace, a building efficiency baseline) still appears in the table with its own raw values; only a genuinely null field renders "—". The bucket is matched by comparing `isoDate(periodStartFor(...))` to the `bucketStartDate` **string**, never by parsing it back into a `Date` — `bucketStartDate` is a LOCAL `YYYY-MM-DD` while `new Date("YYYY-MM-DD")` parses as UTC midnight, so a Date-to-Date comparison silently matches nothing west of UTC (see §6). Surface: clicking a dot in `RunAnalysisSection` selects that bucket (custom `dot` render prop — selected dot enlarged + ringed, null-valued buckets render no dot and are unclickable, `isAnimationActive={false}` + `activeDot={false}`, mirroring `WeeklyLoadTile`'s established click-to-select pattern), revealing a "Show runs"/"Hide runs" toggle and the `RunBucketTable` drill-down (`src/components/insights/RunBucketTable.tsx`): columns Date · Distance · Pace · HR · Cadence · Efficiency · Load, rows navigate to `/runs/[id]`, horizontally scrollable rather than dropping columns. `RunBucketTable` takes **both** the bucket's `runs` and the full `allWorkouts` population — efficiency must be scored over the full set (`scoreWorkoutsEfficiency` needs `MIN_BASELINE_RUNS`=5 neighbours; a weekly bucket holds ~1–4 runs, so scoring the bucket alone would render the entire Efficiency column as "—"). Any change to `selectedMetrics`/window/`minMiles`/`maxMiles` clears the selection and closes the table, since the selected bucket may not exist under the new filters (`selectedMetrics` is compared by REFERENCE, which is exactly why a rejected pill click must return the previous array identity). In dual-metric mode **both** lines render their own dot at a bucket and both are enlarged/ringed when it is selected; either one's click writes the same `bucketStartDate`, so no de-duplication is needed, and a bucket where only one metric resolved is still selectable via that metric's dot. No new Firestore reads — everything derives from the already-fetched workouts array.

7d. **Consistency credit for the plan-completion projection** (`src/utils/planConsistency.ts`, applied at `src/app/(app)/plan-insights/page.tsx`): §7c's raw projection can only move based on race-effort-tier evidence in the Riegel fit, so a well-executed, properly-paced plan (correctly-paced easy long runs, which never register as "quality") can show flat/worse progress despite real training happening — confirmed by a same-day investigation of the active plan's real weeks 9–16. This is a SEPARATE, bounded, POST-HOC layer on top of `buildAnchoredPredictionProjection`'s output — it does NOT add points to the Riegel regression and does NOT touch `predictRaceTime`/`fitRiegel`/`buildPredictionProjection`/`buildAnchoredPredictionProjection` (all byte-unchanged; a prior attempt to blend a similar signal INTO the fit itself — the fast-finish `minMilesForFit` bypass — produced a far larger effect than intended and was reverted; see §6 #28 Follow-up #3). Signal: a 50/50 blend of two ALREADY-COMPUTED app signals, no new fitness model — (1) weekly adherence % (`buildPlanAdherence`'s `weeksHitTarget`/`weeksWithPlan`, the SAME 85% completion rule from commit `877cdce`, already shown on the page's Adherence card) and (2) CTL ramp-trend health (`trainingLoadSeries.ts`'s `trendVsPast`, comparing today's CTL to 4 weeks ago — the SAME lookback Personal Insights already uses for its own CTL trend arrows, seeded via the SAME `CTL_IMPACT_SEED_DAYS=180` `computeCtlImpact` uses). `computeConsistencyScore` blend: adherence fraction = `weeksHitTarget/weeksWithPlan` (0 when `weeksWithPlan < MIN_WEEKS_FOR_ADHERENCE_SIGNAL=2` — too little data, returns 0 OUTRIGHT, not an error/penalty); ramp fraction from `ctlTrend.direction` — "down"→0 (credit-only layer, so no credit is the floor, not a penalty), "flat"→0.5, "up"→`clamp(pct/RAMP_TREND_FULL_CREDIT_PCT=20, 0, 1)`, `null`→0 (insufficient load history); `consistencyScore = (adherenceFraction + rampFraction) / 2`. Mapped to `consistencyAdjustmentPct = -(score × CONSISTENCY_ADJUSTMENT_MAX_PCT=0.02)`, clamped to `[-0.02, 0]` — **ONE-DIRECTIONAL, never positive**: this can only reduce the projected finish (credit), never increase it. `applyConsistencyAdjustment` multiplies every non-null point in the anchored projection by `(1+adjustmentPct)` uniformly (computed ONCE as of today, not recomputed per week); null points (unfittable weeks) pass through unchanged. **Separate budget from §7c's `MAX_PROJECTION_ADJUSTMENT_PCT=0.04` anchor clamp** — the two are never combined into one number. **Scope**: Plan Insights forward projection ONLY — `predictRaceTime`/`computeRunImpact` (run-detail "This Run's Impact", Races page) never import or receive any `planConsistency.ts` output; regression-tested. **Disclosed in the UI, never silent**: `PredictionTrendChart`'s caption always states the up-to-2% credit and its CURRENT applied value (including when it's 0%) whenever the dashed projection is shown. Real-data verification (2026-07-10): 75% adherence (6/8 weeks) + CTL +8.5%/4wk → `consistencyScore≈0.588` → `-1.18%` adjustment → race-day projection moved from 2:11:19 to 2:09:47 (−92.6s). All four constants (`CONSISTENCY_ADJUSTMENT_MAX_PCT`, `MIN_WEEKS_FOR_ADHERENCE_SIGNAL`, `RAMP_TREND_FULL_CREDIT_PCT`, and the 50/50 blend weighting) are JUDGMENT CALLS, not derived — tune from production QA.

1. **Per-point HR now exists on the `route` subcollection** (field `hr: number | null`, added iOS commit 84dfbf3). Run Detail HR-zone breakdown (`ZoneBreakdown`) and Training Load consumers now read `users/{uid}/settings/prefs.maxHeartRate` when set and otherwise fall back to `DEFAULT_MAX_HR=185` through `resolveMaxHr(settings)`. 22. **Enrich-on-load: store-early-then-upgrade + the snapshot-loop guard** (`useEnrichTrainingLoads`, `enrichTrainingLoads`, `shouldEnrichLoad`/`enrichBasisKey` — Section 5 item 4a): iOS writes each `healthWorkouts` doc in two phases (base doc first, then `avgHeartRate` + the `hrStream` subcollection in a LATER write) and never writes a load, so a freshly-synced workout legitimately exists for one or more sync cycles with no stored load and sometimes no HR basis at all. Enrich-on-load auto-stores the load once the workout loads in the app. Three things to keep in mind: (a) **store-early-then-upgrade** — a workout whose `hrStream` hasn't landed yet is stored from its avg HR (`method:"avg-hr-fallback"`); because `resolveDisplayLoad` prefers a finite stored value FOREVER, that early value would permanently mask the better streamed value UNLESS it is re-enriched. The UPGRADE branch of `shouldEnrichLoad` does exactly that — when `hasRoute`/`hasHRStream` later flips true it re-runs once and rewrites `method:"streamed"`. (b) **refetch loop** (formerly "snapshot loop" — `AppDataContext.workouts` was a live `onSnapshot` listener before 2026-07-17; see §2 "Workouts fetch pattern") — an enrich write is picked up on the next `refreshWorkouts()` call (tab-focus or manual refresh), which re-runs the effect on its own prior output the same way a listener re-fire used to. The guard is `enrichBasisKey(workout)` = `id|hasRoute|hasHRStream`: each workout's basis is recorded the moment it's queued, so the same `(workout, basis)` is never enriched twice. This is what stops a compute that legitimately yields **null** (no usable HR — e.g. `hasHRStream` true but a sparse/empty stream and no avgHR) from re-writing the same null forever; a workout only re-qualifies when its basis genuinely changes (the stream arrives), which is the one upgrade we want. An `inFlightRef` additionally blocks overlapping passes. (c) **settling guard** — the hook waits until `settings !== undefined` (the profile fetch has resolved) before enriching, so it never stores loads against the DEFAULT HR anchors and then masks the correct value; a resolved `null` profile is fine (defaults are then intentional, and a later anchor change recomputes via §6 #21). **Coverage caveat**: each page only enriches the set IT loads — Workouts (non-runs) and Runs (runs), and only the loaded window (limit 1000, shared via `AppDataContext`). A workout in neither loaded set isn't auto-stored until one of those pages loads it; its display is unaffected (live `resolveDisplayLoad`), and the settings-recompute / backfill remain the bulk write paths. Real Watch flush timing is only observable on-device.

44. **The Riegel race-prediction trend inherited the same UTC-midnight plan-start parse — every weekly point was computed a full day early, and the chart's first week often had no point at all.** `src/utils/racePrediction.ts` (`buildPredictionTrend`) and `src/utils/predictionTrend.ts` (`buildPredictionProjection`) both derived `planStart` with `new Date(plan.startDate)`, so each week's window ran **Sun ~20:00 → Sat 23:59:59.999** instead of Mon 00:00 → Sun 23:59:59.999 (see §6 #43 for the mechanism).

    **Why it mattered more here than a label shift**: the week END is the prediction's `asOf`, and `asOf` is the reference for the entire model — the 56-day ordinary-run cutoff, the 120-day race-anchor memory, the `startMs > asOf` exclusion, every effort's `ageDays` (hence the 5-week half-life decay), the trailing-28d easy-pace median that drives QUALITY tiering, and the best-effort segment filter. Shifting it 24h early therefore changes **which runs are in the fit, what tier they get, and how they are weighted** — not just when the point is plotted. In `predictionTrend.ts` the same bad `planStart` also fed `plannedEntryDate`, dating every synthetic planned run one day early.

    **Fixed** by parsing through `parseLocalDate`, matching `buildPlanAdherence`. The Riegel model itself is **untouched** — k-clamp `[1.04, 1.10]`, RACE ×3 weight with 120-day memory, 5-week half-life decay, QUALITY ×1.75, the HR-gate, and the regression are all unchanged. Only the reference date moved; every k/weight/decay difference below is a **mechanical** consequence of a different effort set and different ages, not a re-tuned parameter.

    **Real-data impact: material.** Both functions were run over this user's five plans from the local snapshot (`scripts/snapshots/`, exported 2026-07-24) before and after, in `America/New_York`, at the half-marathon target with and without best-effort segments. On the active "Sub 9:09" plan (production config, best-efforts on), **9 of 10 elapsed weeks changed**: **W1 went from _no prediction at all_ to 2:21:40** — the buggy Saturday `asOf` left only 3 qualifying efforts, below `fitRiegel`'s minimum of 4, so the chart's first point was simply missing; W2 2:20:52 → 2:19:52 (−60.1 s); W3 2:18:58 → 2:18:42 (−15.5 s); W5 2:13:47 → 2:14:28 (+40.6 s) **with k 1.04000 → 1.04338**, moving off the clamp floor; W6 +5.8 s; W9 −4.0 s; W10 (latest) unchanged. Across the other plans the largest moves were **−127.3 s** ("Gym Rat" W2 / "Spring 2026" W14), **−74.5 s with k 1.08863 → 1.07571** (Spring 2026 W8), and **+47.9 s with k 1.04576 → 1.05484** (Spring 2026 W10). The **live prediction card is unaffected** — it calls `predictRaceTime` with `asOf = now` and never touches `plan.startDate`. The forward projection moved ≤4 s per point (it is anchored to the live baseline and bounded by `MAX_PROJECTION_ADJUSTMENT_PCT`), but its week-end dates now land on Sunday rather than Saturday. Every changed value was re-derived **independently** — `buildQualifyingEfforts` + `fitRiegel` + `predictSeconds` reimplemented from scratch in plain Node with no import from `src/` — and agreed on all 58 compared (predicted seconds, k, n) to floating-point exactness.

    Coverage: `planWeekWindow.prediction.test.ts` (11 new). Eight fail against the pre-fix source in `America/New_York` and pass after; the other three are deliberate no-change regressions (the live-card path, a week with no boundary-day run) plus a note recording whether the runner's timezone exercises the bug at all — at `TZ=UTC` the two parses coincide and it is invisible. `src/utils/racePrediction.ts`, `src/utils/predictionTrend.ts`, `src/utils/__tests__/planWeekWindow.prediction.test.ts`. The existing `predictionTrend.test.ts` fixture was also corrected from `"2026-06-01T00:00:00"` to the date-only `"2026-06-01"` the read path actually produces (see invariant #12).

45. **Three separate icon sets rendered the same four-state run status, and one of them drew a checkmark for "partial".** `src/components/RunStatusIcon.tsx` documents itself as the single source for `RunEntryStatus` (met / partial / missed / upcoming), but two consumers bypassed it: the dashboard's inline `StatusIcon` (a literal duplicate of the same icons and colors) and `RunningPlanDetail`'s own set, whose **"partial" rendered a bare `Check`** — visually indistinguishable from "met" at 16 px, so a partially-completed run read as done. Both now render `RunStatusIcon`; what the shared component draws is unchanged.

    The dashboard swap is **byte-for-byte identical markup** (verified by rendering both variants), so nothing moves there. In `RunningPlanDetail` the footprint is preserved by passing `size={16}` (the old icons carried `w-4 h-4` = 16 px over lucide's default 24 px attributes) inside the unchanged `w-4 shrink-0` wrapper, so column width and spacing are unchanged; three glyphs and one color intentionally differ — `circle-check-big → circle-check`, **`check → circle-minus`** (the fix), `circle-alert → circle-x`, and "upcoming" `text-border → text-textSecondary` (slightly more visible, since the shared component owns that choice). Coverage: `RunStatusIcon.callSites.test.tsx` (12 new — the canonical four states, "partial" asserted to carry no checkmark of any kind, a rendered `RunningPlanDetail` proving all four route through the shared component with no bare `lucide-check`, and structural assertions pinning the dashboard call site, which cannot be mounted here without stubbing auth/Firestore/the ring stack).

46. **Expensive client-side aggregations need BOTH a readiness gate and a module-level per-key in-flight lock.** Personal Insights' stale `aggregatedStats` path previously read up to 50 complete GPS `route` subcollections in parallel for fastest-mile computation. The route fan-out was removed on 2026-08-20: fastest mile now comes from parent-doc `bestEfforts["1mi"]`; only the unchanged `mileSplits` reads for HR-zone distribution remain. `useAggregatedStats` still waits for `AppDataContext.workoutsLoading`, `settingsLoading`, and `racesLoading` to all clear, then deduplicates the entire cache-check/compute/write operation through a module-level `Map<string, Promise<AggregatedStatsDoc>>` keyed by `uid + the serialized current freshness fingerprint`. Same-key callers await the existing promise; the entry clears in `finally` after success or failure, so a changed input or a failed attempt can retry. The `users/{uid}/insights/aggregatedStats` write is awaited before the promise completes, preserving `computationVersion`, `reviveAggregatedStatsDates`, and `stripUndefined`. Greppable `[aggregated-stats]` events support production verification.

47. **Persisted route-derived values need both an explicit freshness basis and persist-time domain validation.** A compute-only-when-`undefined` guard is unsafe for two-pass sync: an early partial route can persist a plausible value that never refreshes after `routeComplete` flips to true. `bestEfforts` therefore persists route completeness, point count, and algorithm version beside the existing distance keys. A 2026-08-20 production investigation also found that three legacy routes had hundreds of spatially plausible points collapsed into only 2–3 millisecond timestamps; the historical `fastestMileSegment` accepted any positive elapsed value, so the freshness backfill persisted three `0.000476–0.001s` miles. A fourth normally-timestamped route produced a genuine `1575.873s` stopped mile. Computation version 2 now applies the shared strict `180 < seconds < 1200` predicate before persistence and stores `null` otherwise; the aggregation filter remains defense in depth. The web repository has no production route writer—the route subcollection is written by the iOS HealthKit sync—and its snapshot importer is emulator-only and revives Firestore timestamps, so the timestamp-collapse source must be investigated upstream in the iOS repository. Consumers should use the shared recompute predicate and bump `BEST_EFFORTS_COMPUTATION_VERSION` when the underlying fastest-mile algorithm changes; do not infer freshness merely from field presence.

48. **Aggregated Insights has independent main and VO₂ freshness domains.** `users/{uid}/insights/aggregatedStats` now stores an `AggregatedStatsFreshnessFingerprint` beside a `Vo2FreshnessKey` (same document/path; no new rule). The main fingerprint covers computation version, latest workout id, resolved max/resting HR, active race id/date, a deterministic revision of already-loaded overrides, and the local calendar date/year. Because the required schema has no separate workout-revision field, `useAggregatedStats` appends a deterministic revision of already-loaded aggregation inputs (including persisted `bestEfforts` and `trainingLoadV2`) to `overridesRevision`; same-ID enrichment therefore also invalidates the main domain. Those helpers are pure and introduce no reads. The VO₂ key is the latest qualifying sample's local `YYYY-MM-DD`; because that metadata is not present in `AppDataContext`, its current value is derived from the existing bounded 180-day `healthMetrics` query. An unchanged pair returns the cached document without a write; main-only staleness reuses cached VO₂ history, while VO₂-only staleness updates only `vo2History`, `vo2FreshnessKey`, and `computedAt` and skips mile-split/main-stat computation. The formulas remain unchanged. Correctness intentionally increases recomputation when HR/race/override/workout-enrichment/day inputs change; the bounded metrics validation read is the cost trade-off for detecting VO₂-only syncs without a new metadata document/path.

## Section 9 — Local Development

- Local dev uses the Firebase Local Emulator Suite by default to save quota.
- Run `npm run dev:emulators` in one terminal, and `npm run dev` in another.
- To bypass the emulator and connect local dev to production Firestore, set `NEXT_PUBLIC_USE_PROD_FIRESTORE=true` in `.env.local`.
- Production builds (`NODE_ENV !== 'development'`) always use real Firestore, regardless of env vars. This is enforced in code, not just by convention.
- To refresh emulator data from production: `npm run snapshot:export` (reads prod, ~few seconds), then with emulators running, `npm run snapshot:import` (writes to emulator only, safe).
