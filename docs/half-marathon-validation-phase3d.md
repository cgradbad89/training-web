# Half-marathon validation protocol · Phase 3D

Phase 3C found two candidate half marathons and zero independently testable outcomes. The September 22, 2026 archive postdates both races and omits race and override scopes. The October parent and Manual Performance receipts also postdate both races. The latter supplies zero accepted aerobic observations. This phase adds a dormant tool for future evidence and qualifying historical captures. Its code lives in `tools/race-validation/` with a local runner in `scripts/validateHalfMarathon.test.ts`. It has no application entry point or Firebase, network, scheduler, or telemetry client dependency. The application estimator and Phase 3A/3B tools remain separate. See [Phase 3A](race-performance-phase3a.md), [Phase 3B.1](race-confirmation-phase3b1.md), [Phase 3B.2](workout-aware-race-research-phase3b2.md), and [the experimental model](experimental-current-half-marathon.md).

## Study design

- **Claim.** The experiment estimates present capability under appropriate conditions. A later maximal race supplies an imperfect proxy. Even at one day, course, pacing, weather, taper, health, and fueling affect agreement. Predeclare the 1-day comparison as the primary proxy if appropriate for the pilot. Report 7-, 14-, and 28-day results separately as checkpoint-to-event comparisons. A future date-specific forecast needs its own model, prediction receipts, validation, and uncertainty study.
- **Unit.** The event is the outcome. Four checkpoints are four dependent comparisons against one result. The report partitions by lead day and never pools them to inflate the sample. Use one subject per study. Repeated events in the same training block can also be dependent.
- **Timing.** For lead days 28, 14, 7 and 1, subtract calendar days from the local event date. The deadline is the last millisecond of that local checkpoint day. The actual consistent read and computation must occur by that deadline. The model runs at the actual captured data instant, which can precede the deadline. Record that instant and its real custody timestamp separately. No interpolation to the deadline, late snapshots or target-day evidence. Set a stable time-of-day capture window prospectively.
- **Scope.** Supply race records and canonical override scope as of capture and at least the 236 days of workout parents through capture (180-day anchor limit plus the 56 days needed before the oldest anchor). Record any gaps, query limits, and ingestion lag. The bounded source claim describes returned records, not actual training completeness. Retain already-authorized earlier relevant parents when present. Duplicate exact revisions collapse. Conflicting revisions, unknown exact availability, and later revisions without an earlier frozen copy cannot reconstruct the checkpoint. Unknown workout ingestion excludes that workout. Explicit partial/unknown collection coverage yields abstentions.
- **Pre-registration.** Before reviewing outcomes, retain the protocol/model version, exact tool and source code revisions, capture window, outcome qualification, inclusion and coverage thresholds, primary horizon, chronological `testFromDate`, and criteria for bias, absolute error and large errors. The tool separates earlier development outcomes from test outcomes by this date. Independent custody of the preregistration is a study responsibility. Apply any calibration only to development data and lock it before the later test set. Preserve previous artifacts and their versions.
- **Model comparisons.** Execute production `estimateCurrentHalfMarathon` with frozen inputs and the pinned configuration. Report its displayed whole minutes in seconds. The same-anchor comparison uses the exact production anchor, gate and rounding with the adjustment set to zero. Separately report the latest qualified same-distance maximal result and the latest eligible other-distance maximal result converted with existing Riegel 1.06 and Daniels–Gilbert/VDOT helpers. The comparators use the same 180-day domain. Same-anchor can use a production provisional anchor and is reported separately from qualified-only methods.
- **Attribution.** Record exact combined adjustment, volume/frequency, endurance, matched pace and rounding in seconds. Remove each already-blended contribution with pair selection and gates fixed and apply the same rounding. To isolate freshness, recover the unattenuated contribution by dividing by the shared freshness multiplier where positive. Zero freshness makes the unattenuated effect unidentifiable from the output. This counterfactual describes the arithmetic of a frozen checkpoint. It does not identify physiological causality or validate a refitted model.
- **Scoring.** Error is prediction minus actual finish time, so positive bias means too slow. Report absolute error, MAE, signed bias, and count at least 300 seconds wrong. Compare MAE on the common cases where both methods produce a prediction. Availability uses all eligible outcomes at the horizon. Abstention rate uses admitted checkpoints, with missing or excluded artifacts reported separately. An empty denominator produces null. Report quality, missingness and individual large errors alongside means.
- **Sample.** Use the first 3–5 prospective outcomes to test custody and coverage. Determine the untouched test count from the minimum useful paired improvement, observed variability, abstentions, and outcome dependence. Shorter races and measured maximal trials can provide cross-distance anchors. They are a separate target population and cannot inflate the count of half-marathon validation outcomes.

## Portable schema and custody

All files are finite JSON. Use explicit UTC timestamps ending in `Z` and a local date in the target's IANA zone. For the v1 API, an instant must be known and later than the Unix epoch. Every capture has `protocol: "half-marathon-validation-v1"` and a `target` with `subject` (opaque single-subject key), `raceId`, `raceDate`, and `timeZone`. Keep real artifacts in private storage outside Git. Source references should be opaque audit references rather than credentials.

| Capture request field | Required content |
| --- | --- |
| `horizon`, `capturedAt` | One supported lead day and the actual point-in-time source capture. |
| `source` | `kind` (`synthetic`, `prospective_capture`, or `historical_capture`), `reference`, `authorization`, and `codeRevision` identifying the capture implementation. |
| `coverage` | `workouts`, `races` and `overrides` marked `complete`, `partial`, or `unknown`, `workoutsFrom` as a local date or null, and `limitations` as an array of strings. Use an empty array for a missing scope with partial/unknown coverage. |
| `inputs.workouts`, `inputs.races`, `inputs.overrides` | Arrays of `{id, revision, availableAt, doc}`. Each contains the exact version observed by capture. Use the existing parent/race/override field names. Workout start, end and sync clocks must be normalized explicitly. Use known manual `updatedAt` as the **model's** sync surrogate when adapting a manual parent, separately from proof of exact revision availability. Unknown sync remains null. |
| `inputs.features` | Optional compact references with `workoutId`, `parentRevision`, `revision`, `digest`, `status`, `extractorVersion`, `qualityPolicyVersion`, `extractedAt`, and `availableAt`. Requires accepted status, matched eligible parent and dates by actual capture for compatibility. Compatibility is a potential research input only. The tool does not acquire feature values or feed them to models. |

The sealed checkpoint adds a stable subject/event/date/zone/horizon key, the resolved date and cutoff, separate input and full artifact SHA-256 digests, versioned predictions or explicit abstentions, anchor qualification, eligible workout IDs, exclusions, and attribution. Canonical JSON sorts object keys and canonicalizes revisions by ID. The output writer creates files exclusively. Replay verifies the full digest and recomputes the entire checkpoint, refusing changed model versions, outputs or evidence. If a model or any dependency changes in a way that could affect outputs, preserve the pinned code for old replays and version future checkpoints.

An integrity digest is not proof of timing or independent review. Real studies require a separately sourced **custody catalog**. The tool checks its entries against the artifacts. The trusted operator must establish catalog authenticity and verify the referenced external evidence.

| Receipt kind | Required independent evidence |
| --- | --- |
| `checkpoint` | The full prospective artifact digest existed by the cutoff, with custody time at or after capture. Use the original object-generation receipt in an independently managed, write-once location. |
| `historical_input` | The normalized input digest maps exactly to a separately timestamped original capture, and that capture existed by the checkpoint deadline. A reviewer may verify the projection later, but records the timestamp of the original evidence. Keep the mapping and original digest as part of the referenced custody evidence. |
| `outcome` | An independent review pins the qualified result, distance and timing provenance at or after the outcome evidence became available. The recorded review can be later than the event. |

Each entry is `{kind, digest, anchoredAt, reference}`. `anchoredAt` is the externally established receipt time, not a date typed into the artifact. For historical inputs use `inputDigest`. For prospective checkpoints and outcomes use `integrityDigest`. The scorer separates historical replay, genuinely prospective predictions, and simulations. Importing today's Firestore data, changing the clock, or rehashing a checkpoint cannot establish a missing historical receipt. Client-writable confirmation documents can supply dated result details in a separately frozen capture. A client save timestamp by itself cannot prove those details were available in the past.

## Outcome intake and local commands

Use an independently timed maximal half marathon on a measured course. Record official event name, event date, nominal distance, chip or official elapsed finish seconds, the timing and course references, effort attestation and conditions. A measured time trial can use independent elapsed timing. Include recorded duration, recorded elapsed time, linked workout ID when known, and an explanation for disagreement greater than the existing timing tolerance. GPS overdistance is not rescaled. An owner can attest effort or explain clocks, but owner-only time without independent timing does not qualify in v1. The intake preserves excluded candidates with explicit reasons.

April 26, 2026 PNC Half Marathon still needs independent timing and an explanation of its approximately 629-second device clock discrepancy. September 20, 2026 DC Half Marathon has agreeing recorded clocks, with official timing still missing. Both need documented maximal effort, conditions and result provenance. Do not use workout duration as official timing. Even after qualifying both labels, their historical predictions need separate pre-cutoff custody.

Run from the repository root, with installed dependencies and authorized files outside Git.

```sh
# Each command uses a fresh, private output path.
PHASE3D_MODE=checkpoint PHASE3D_INPUT=/private/tmp/capture.json \
  PHASE3D_OUTPUT=/private/tmp/checkpoint.json \
  TZ=America/New_York npm test -- scripts/validateHalfMarathon.test.ts

PHASE3D_MODE=outcome PHASE3D_INPUT=/private/tmp/outcome-intake.json \
  PHASE3D_OUTPUT=/private/tmp/outcome.json \
  TZ=America/New_York npm test -- scripts/validateHalfMarathon.test.ts

PHASE3D_MODE=evaluate PHASE3D_INPUT=/private/tmp/study.json \
  PHASE3D_CUSTODY=/private/tmp/reviewed-custody.json \
  PHASE3D_OUTPUT=/private/tmp/report.json PHASE3D_MARKDOWN=/private/tmp/report.md \
  TZ=America/New_York npm test -- scripts/validateHalfMarathon.test.ts

# Synthetic end-to-end examples, with no files or credentials to supply.
TZ=America/New_York npm test -- tools/race-validation/validation.test.ts
```

`outcome-intake.json` takes `protocol`, `target`, `dataKind`, `name`, `kind` (`official_race` or `measured_time_trial`), `distanceMeters`, `finishSeconds`, `timingBasis` (`chip`, `official_elapsed`, `independent_elapsed` or `unverified`), `recordedDurationSeconds`, `recordedElapsedSeconds`, `workoutId`, `timingReconciliation`, `effort` (`maximal`, `nonmaximal`, or `unknown`), `effortSource`, `conditions`, and `source: {timingReference, distanceReference, knownAt}`. Use null for missing clocks/references. Fields required for qualification will appear in `qualificationReasons` when missing.

The study file contains `{protocol, subject, dataKind, captureKind, testFromDate, checkpoints, outcomes}`. Embed the sealed objects in the last two arrays. Use `dataKind: "real"` with the appropriate capture kind, or `dataKind: "synthetic"` without a custody file. The runner reads only explicit local JSON files up to 32 MiB. Use a fresh output path if a prior run already created a file. Resolve a digest or version error by recovering the original artifact and tool revision. Resolve competing captures by verifying original custody before preparing a new study manifest. Record a missing checkpoint when an authorized capture was missed; a later rerun may replay an intact artifact but cannot create an earlier one.

## Automatic capture options and activation boundary

| Option | Practical tradeoff |
| --- | --- |
| Existing app session | Reuses loaded parent data with zero incremental capture reads. Sessions are optional, cache and source refresh can straddle a cutoff, and browser clocks/metadata are insufficient for independent custody. |
| Existing authenticated server request | Gives a server clock and access to owner authentication. A user-triggered request still misses days with no app activity. The Coach call is not a suitable dependency for a fixed study schedule. |
| Narrow scheduled server read | Can capture during a predeclared window without owner activity, use a consistent Firestore read snapshot, and deposit an independently timestamped generation. Requires explicit production authorization, scoped credentials and approved private storage. |
| Local offline | Current code can seal and score already-authorized captures. Suitable for synthetic/research use. Local filesystem timestamps alone cannot establish custody, and manual export for each checkpoint is unsuitable for ongoing collection. |

**Recommended activation design.** Use one daily Vercel Node.js cron during the pilot in an existing project and a pre-registered calendar of enrolled race IDs in server-only configuration. A single UTC slot such as 16:00 keeps the capture safely inside the New York local day across DST, even with Hobby's hour-wide start window. The pure `dueCheckpoints` helper returns due keys only. Idle invocations can return without database access. On a due day, resolve a consistent server read point for bounded parent, race and override queries. Capture the authoritative read timestamp and exact document revisions. Enforce the single-owner subject boundary and narrow service access, including checks before any database call. Pass normalized summaries to `sealCheckpoint`. Begin with parent-only inputs. Optional features can be added from existing compatible receipts after reviewing their incremental read and custody cost.

Write a canonical artifact keyed by subject/event/date/zone/horizon to an existing **approved private Google Cloud Storage location in the Firebase project**, if one meets the access, retention and cost requirements. Use create-only credentials, `ifGenerationMatch=0`, and verify the original generation, service creation time and artifact digest through a separately authorized read identity. Owner/browser access must not allow mutation or overwrite. A digest alone or a mutable Firestore document is insufficient. Confirm existing bucket eligibility and retention before designing the deployment; an unsuitable or unavailable bucket leaves capture dormant. This design requires no Firestore collection, indexes or rule changes. [Generation preconditions](https://docs.cloud.google.com/storage/docs/request-preconditions)

**Incremental usage estimate.** The delivered offline code adds zero Firestore operations, runtime functions, scheduled executions, persistent cloud bytes or paid-service dependencies. For the dormant design, budget up to 31 cron invocations per month during a pilot and four captures per enrolled race. Example caps are 1,000 workout, 100 race and 1,000 override documents, with one overflow probe per query. The worst case for one race is 8,412 reads per month before retries, 0 Firestore writes and 4 private object creates. Typical counts will depend on the bounded queries and active enrollment. Review query minima, index entry charges, network, project-wide quota, and storage policy before activation.

With headroom in existing quotas, incremental charges should be $0. As an illustrative over-quota estimate, 8,412 reads at $0.03 per 100,000 in `us-central1` cost about $0.003, excluding index and network charges. Four regional Standard object creates and at most 4 MiB of retained new data are less than $0.001 for the first month at example regional rates. At `iad1`, 31 invocations assuming 2 GB, 27 one-second idle calls and 4 ten-second captures, with respectively 0.1 and 1 active CPU seconds per call, add less than $0.001 of metered function usage at published rates. This excludes plan fees, future accumulation, egress and retries. Actual plan, region, headroom and bucket availability are unverified. [Firestore pricing](https://firebase.google.com/docs/firestore/standard-edition), [Vercel cron limits](https://vercel.com/docs/cron-jobs/usage-and-pricing), [Vercel compute rates](https://vercel.com/docs/functions/usage-and-pricing), [Cloud Storage rates](https://cloud.google.com/storage/pricing)

**Recovery and activation.** Vercel cron can miss a run or deliver duplicate invocations, and does not retry failures automatically. Keep the first independently sealed artifact for a key. A duplicate create conflict verifies the existing digest and original timestamp and never replaces it. An authorized retry before the same deadline can capture if the key is empty. After cutoff, record a missing checkpoint with the failure reason. When query caps or source failures prevent a complete read, save an explicit abstention only if custody and available inputs are trustworthy. Log status, counts and an opaque key without health payloads. Verify access, scheduler window, cap handling, dry-run receipts, storage retention and expected billing on synthetic or approved non-production infrastructure before enabling any schedule, read or writer. Require owner authorization for production data access, credentials/retention, deployment of a collector, and any recurring charge. [Vercel cron behavior and recovery](https://vercel.com/docs/cron-jobs/manage-cron-jobs)
