## Distinct code paths

1. **Legacy pace prediction** — `src/app/(app)/personal-insights/page.tsx` disables `buildQualifyingEfforts`/`fitRiegel` when race-performance display is enabled. `src/utils/racePrediction.ts` exposes the older training-effort fit and weekly trend; `riegelFit.ts` uses 56-day ordinary-run / 120-day race-matched windows and RACE/QUALITY/BASELINE weighting. Race matching there operates on workouts and date/distance, not the modern confirmed-result pipeline. `Race.targetPaceSecondsPerMile` is a goal; `result`, `actualRunDurationSeconds`, `actualRunId` and confirmation history describe achieved evidence. Changing the old fit or the goal cannot fix the table in the screenshot.
2. **Live four-distance pipeline** — `CurrentFitnessTable.tsx` → `computeCurrentFitness` in `hybridCurrentFitness.ts` → shared prediction-only `treatConfirmedRacesAsMaximal` adapter → official v2 / HR-enhanced corroboration → `estimateHybridCurrentFitness` → `estimateHybridHalfMarathonV11` with each `hybridTargetProfiles.ts` target. Production feature gates live in `racePerformanceGate.ts`. Plan Insights and race-day forecast are separate consumers; do not substitute their outputs.
3. **Actual race-result integrity** — `racePerformance.ts:buildRaceEvidence` selects the confirmation valid at cutoff, checks chronology, linked workout identity/date/type/distance/timing, exclusions and conflicting results. A valid confirmation supplies finish seconds; otherwise a usable linked workout supplies duration, then entered result is only unverified fallback. `evidenceQualification.ts` admits eligible confirmed races, or timing-consistent recorded races with usable workout timing; a result string alone does not automatically qualify. The owner-approved adapter reinterprets confirmed hard/nonmaximal effort in copies for prediction, without changing stored attestations or applying subjective effort percentages. Unknown effort and integrity failures stay excluded; the demonstrated-race policy is the separate rollback fallback.
4. **Recency and independent evidence** — qualification expires items **over 180 days** (`evidenceQualification.ts`, `evidenceSegments.ts`) and deduplicates correlated workout/day evidence. `evidenceCombination.ts` adds measurement variance (confirmed race 1%, recorded 1.5%), target-conversion variance and age drift `0.01 * sqrt(ageDays/30)`, then pools race and recent-effort groups by precision, including common-mode terms. Effective shares sum to one; base seconds are `exp(sum(share * ln(convertedSeconds)))`. A lone valid race can retain all the base weight while becoming less certain. If races are absent, corroborated contemporary efforts must satisfy their own sufficiency checks. Ordinary training does not become maximal evidence.
5. **Evidence quality versus display confidence** — combination quality is adequate only with no within-group contradiction, internal uncertainty ≤2%, and a confirmed race or ≥3 observations. This is not calibrated accuracy. `hybridPerformanceV11.ts` separately restricts status/confidence for conflict, distant conversion, unknown readiness, dominant race age **over 42 days**, durability and other limitations. Moderate also requires readiness ≥0.5. `currentFitnessFormat.ts:confidenceLabel` maps unavailable → Insufficient evidence and the computed confidence → Low/Moderate under the UI's Evidence quality column. Thus underlying `adequate` quality can still legitimately display Low. The screenshot's 5K precision message does not establish its exact evidence mix; do not infer a distant-evidence restriction absent from the screenshot.
6. **Training readiness** — `enduranceReadiness.ts` deliberately excludes linked race workouts: a single race is performance evidence, not a training pattern. It uses eight trailing weeks strictly before the cutoff; fewer than four observed weeks is unknown, not inactivity. Long-run input is the mean of the three largest weekly-longest non-race runs; volume/frequency use observed weeks. Score weights are 0.5 long-run / 0.3 volume / 0.2 frequency, smoothed over seven daily offsets. A September 20 half is still inside the nominal 56-day window on November 12, but is deliberately excluded as a race.
7. **Endurance and marathon gates** — `hybridPerformanceV11.ts:estimateCore` first computes the weighted converted base, then checks endurance support: `max(readiness, atTargetShare) >= 0.2` when readiness is known. The at-target band is target/source ratio 0.8–1.25; HM→marathon ratio 2 is outside it. For 5K/10 miles a longer race can support the floor; that waiver does not establish marathon endurance. Next, absent ≥50% at-target marathon evidence, marathon durability requires known readiness and longest recent non-race run ≥12 miles. Below 16 miles for the top-three mean or 20 mi/week remains provisional/Low. These thresholds are documented engineering choices, not validated facts. **The first floor can withhold the number before the 12-mile durability branch runs.** The UI maps all `insufficient_endurance_preparation` marathon causes to the same 12+ wording, so the screenshot cannot identify the exact failing gate or establish that adding one 12-mile run would release a time.
8. **Conversion and bounded adjustments** — the marathon shorter-source exponent is `1.06 + (1.15 - 1.06) * (1 - readiness)` (unknown readiness uses the base exponent, with withholding still enforced). Marathon conversion uncertainty is `0.04 * abs(ln(target/source))`; HM→marathon adds ~2.77% before measurement, age and common-mode terms. Physiology and at-target readiness-change adjustments are separate, bounded and correlated-term-aware (total ≤3%). A half marathon is already a weighted marathon anchor; **the final finish time is deliberately null after the preparation gate**. Replacing the gate with a simple 2× race time would change both the documented model and its meaning.

## Recommendation and concrete owner decision

**Keep existing numerical outputs, Low labels, expiry, integrity screens and readiness gates.** The recorded half should be a weighted anchor, and already is. Upgrading evidence solely because a result exists would conceal conversion uncertainty, stale dominance or limited preparation. The current table answers what could reasonably be raced today; removing its preparation gates is a product/model policy change, not an unequivocal bug fix.

**Deferred — separate explanation-improvement proposal (not approved for this implementation):** improve the marathon explanation, deriving it from the actual unavailable reason/structured gate rather than the generic 12-mile message. When, and only when, `estimate.combination.items` contains a half-marathon race with positive effective share, add: **“Your half-marathon result is included in performance evidence. Recent non-race training does not yet support a current marathon estimate.”** Distinguish low endurance score, unknown history, and longest-run shortfall, with actual computed values where available. Preserve all simultaneous restrictions. This requires no new reads or writes. Do not assert the half is used when it failed qualification, expired, was superseded or contributes zero weight.

**Original benchmark proposal (now approved and implemented below):** If the owner also wants a number despite that gate, approve a **separate “Marathon equivalent from race evidence — Low; marathon readiness not demonstrated” benchmark**, outside the current-fitness predicted-finish cell. Reuse the existing qualified, age/precision-weighted `combination.baseSeconds` conversion (with explicit source date, age and shares); do not re-add the same race, use goal pace, discount subjective effort or call it a forecast. Require known readiness for this initial scope so unknown readiness does not silently use an optimistic default exponent. Any assumption-sensitivity display needs the same pure conversion variants, separately labelled, not a probability interval; a null post-gate sensitivity range must not be fabricated. Keep the current-fitness cell withheld, preserve other distances and Plan Insights, and version any new output contract. The owner approved this separate benchmark on November 12; implementation is recorded below. Replacing the existing prediction gate would still require a separately reviewed change.

- All four existing finish times, statuses, confidence restrictions and golden parity fixtures remain equal. No Moderate promotion from an added explanation or benchmark.
