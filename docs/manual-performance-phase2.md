## Evidence and bounded work

The review requests the latest 300 workout parents before filtering runs, each run's feature record, matching overrides in batches of 30 IDs, and the current publication revision. At most three new runs are preselected. The user can select older runs; any explicitly selected run retrieves fresh children even when an existing feature and parent match. At most 20 runs can be selected per invocation. There is no automatic historical backfill. Older runs outside the newest 300 parent bound are currently unavailable in this review; extending historical navigation/backfill is deferred.

Confirmation refreshes parent metadata, overrides and feature records. Fresh children use server-only document-ID pagination (250 documents/page), bypassing route/chart/HR caches. A shared budget initially allows 5,000 returned child documents. The UI allows an explicit retry up to 25,000; the module's internal hard ceiling is 100,000 and its supported HR-sample ceiling is 100,000. No run exceeding acquisition bounds produces a truncated feature. An exact full page at the budget limit conservatively fails because exhaustion cannot be proven without another query. Earlier successfully committed features survive later failure. A retry processes explicitly selected runs again; unselected compatible receipts are reused.

Route positions and timestamps produce speed; the Phase 1 policy validates elapsed/workout duration, distance agreement, sample validity, interval gaps, terrain, weather and measured time/HR coverage. Adequate route HR avoids a second HR-stream acquisition. Otherwise bounded chunks supply nearby HR observations. Segments remain grouped under one workout ID. Missing data, absent completion markers, incomplete routes, nonfinite samples and unsupported sources remain limited/rejected/unresolved. Parent/override membership and relevant digests are read again before calculation; a detectable change aborts publication. This does not fence iOS child writers.

Saved features contain a compact effective-workout extraction receipt, content/input digests, versions, observations, coverage and reasons. They contain no raw coordinates or HR streams. Reuse verifies the stored receipt's input/policy versions and matching relevant current parent/override digest. It describes **the last supplied extraction**, never proof that live children remain unchanged. Parent route/HR flags, counts, user confirmation and `syncedAt` cannot prove scientific ingestion completeness. Silent child corrections, stale tails and child changes during a paginated read remain explicit limitations. Forced reprocessing is the manual repair path.

The summary retains Phase 1's distinct race, aerobic, device VO₂ and preparation outputs. Race dates/durations come from actual linked workout evidence; official timing remains unverified. No September race is hardcoded into an empty account. Daily VO₂ records currently lack verified source identity/units, so they retain dates/values and an insufficient comparable-source trend. All history coverage is conservatively partial. More mileage or a new easy run does not produce a numerical race forecast. `estimatedSeconds` and `confidenceInterval` remain null.

## Publication invariant

Every operation is bound to the current Firebase User object, verified owner token claims, UID and AuthContext session epoch. Assertions surround asynchronous work and each transaction attempt. Sign-out, account change and same-UID replacement invalidate the operation. A transaction already sent while authorized cannot be recalled; the client suppresses completion after a session change. Firebase rules remain the authorization boundary.

Feature writes use revision compare-and-swap transactions, with semantic equality excluding extraction time for idempotent retries. Before calculating, the workflow reads the saved feature set and confirms that each selected saved receipt still has its returned revision/digest. Matching dated receipts enter provenance and publication checks whether accepted, rejected or unresolved; inclusion is not aerobic eligibility or proof of unchanged children. Final publication transaction rereads every incorporated feature's revision/digest, compares the expected current publication revision, and atomically creates the immutable snapshot plus current pointer/result. A changed feature or current revision aborts rather than overwriting newer work. Two tabs/devices may perform duplicate reads; only compatible receipts can be published, with current revision deciding the winner. A browser-local in-flight guard also prevents duplicate submissions in the same module instance.

A stable publication digest covers relevant inputs, membership, versions, windows, limitations and result; it excludes actual calculation/extraction clock metadata. Phase 1's full as-of evidence digest is preserved inside each actual receipt. An unchanged same-window recalculation retains the prior saved timestamp/snapshot. A meaningful newly incorporated workout or corrected evidence changes identity even when rounded metrics do not move. Changing observation windows may also change meaning. Snapshot IDs hash the stable publication digest plus expected prior revision, supporting multiple receipts per day and recovery after a lost acknowledgement. Identical current evidence returns unchanged; an obsolete different result conflicts. Returning to old evidence after an intervening publication has a new prior revision and creates a genuine new receipt.

Feature transactions may commit before final publication; failed publication leaves the previous summary intact. Only online Firestore transactions write performance data, avoiding offline queued `setDoc`/batch publication on reconnection. Rules enforce owner isolation, document shape, revision progression, immutable snapshots and paired current/snapshot publication; rules cannot independently recompute scientific hashes or iterate through 300 features. Client verification supplies that additional correctness invariant. There is no source journal, global writer fence or claim of a single immutable telemetry generation.

## Cost report

These are operation estimates from code paths and focused tests, **not production billing measurements**. No production Firestore telemetry was read or written for this implementation. Counts refer to returned query documents; individual missing feature/current document lookups count one read request. Empty queries can still incur a minimum billed read. Rule-dependent `get`/`getAfter` reads and transaction retries can add billed reads. See [Firestore pricing](https://firebase.google.com/docs/firestore/pricing), [transactions](https://firebase.google.com/docs/firestore/manage-data/transactions) and [quotas](https://firebase.google.com/docs/firestore/quotas).

Variables: P ≤ 300 returned parent documents; R ≤ P running parents; O ≤ R returned matching override documents; D ≤ 100 race records; H ≤ 181 health records (180 calendar days normally ≤180 daily documents); B ≤ selected child budget; N ≤ 20 selected feature transactions; F ≤ R incorporated compatible saved features. Every phase reread can have different counts if history changes.

| Action | Additional document reads | Writes |
|---|---:|---:|
| Fresh saved-result panel | 1 current document request | 0 |
| Open review | P + R + O + 1 | 0 |
| Confirm/process (after review) | 2P + 2O + 2R + B + N + D + H + F + 2 | ≤N changed features + 2 publication docs |
| One new run | Same bounded metadata overhead + that run's returned route/needed HR docs | ≤1 feature + current + snapshot |
| Three new runs | Same metadata overhead + combined route/needed HR docs; 3×1,800 points exceeds the 5,000 default and requires explicit higher-budget retry | ≤3 features + current + snapshot |
| Force one old run | Same as one new run; **all selected child docs fetched fresh** | 0–1 feature + 0 or 2 publication docs |
| Save summary/create snapshot | F + 2 transaction reads (current, F features, missing new snapshot) | 2 atomically |
| Unchanged final publication | F + 1 transaction reads | 0 |
| Retry after feature failure | Repeat explicit workflow; successful prior receipts remain reusable when unselected | Only changed/new features, then 0 or 2 publication docs |
| Lost final acknowledgement | Retry reads/revalidates evidence; matching current returns unchanged | 0 duplicate history writes |

The confirm formula includes two bounded parent/override reads (start and before calculation), two feature-list reads (before/after selected writes), estimated one read per feature transaction, supporting evidence and final publication. The UI reports returned source/child documents, individual feature/current lookups, estimated feature-transaction reads and actual final transaction reads. Feature-transaction retry attempts are not individually exposed by that API; displayed totals are estimates in that case. Failures retain progress to the last completed operation; the read-budget exception includes the actual child total. No claim of exact billing is made.

For example P=300, R=200, O=10, D=2, H=100 and F=10: review is 511 reads. Confirmation's fixed metadata/publication overhead is 1,134 plus B + N. One 1,801-point run adds 1,802 reads (2,936 confirmation / 3,447 including review). Three 1,201-point runs add 3,606 (4,740 confirmation / 5,251 including review); three 1,801-point runs cannot finish at the default child budget. Actual point density/HR chunks vary. This explicit-review overhead is additional to AppData's existing newest-1,000 parent workout load; normal saved display adds only one document and zero raw telemetry reads.

Storage is compact JSON, bounded to 700,000 UTF-8 bytes per feature input and publication payload+revision list (below Firestore's document limit; field/index limits still apply). Typical synthetic fixture features are a few KB; current/snapshot size grows with at most 300 feature references, 180 daily VO₂ entries and compact summary arrays. A meaningful publication stores two result copies (one current, one historical); each unchanged click adds zero snapshots. Historical receipts accumulate only from meaningful explicit calculations. No repeated raw samples are stored.

Vercel function executions added: **0**. Calculations run in the authorized browser; Firestore operations use the client SDK. There is no recurring Vercel Active CPU, raw-history hydration on saved display, automatic backfill, dependency change or Firebase deployment.
